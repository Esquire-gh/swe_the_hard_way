Part three · the conversation

06 · Requests and responses

There is a word at the front of every address you have ever typed, http or https, and almost nobody has read what it stands for. The last chapter left a client and a server facing each other, written by strangers years apart, with nothing agreed between them. This chapter is the agreement, and the surprise is how little of it there is. What travels between a browser and a server is text, in lines, and you can read all of it.

An agreement designed to be read by people

The rules are called the Hypertext Transfer Protocol, and the letters are HTTP. The first version was one line long: the client sent GET and a path, the server sent the document and closed the connection. No headers, no status codes, no way to send anything but a document. Every piece added since then was added because something specific did not work, which is the only reason to keep the history in mind at all.

The first line of a request is the request line, three fields separated by single spaces. The method says what you want done: GET means send me this, POST means here is some data, do something with it. The path is the last part of the URL. The version tells the server which rules the client is speaking. Everything after that until the blank line is a header, one per line, written as a name, a colon, and a value. Headers are notes about the message rather than the message itself.

The first line of a response is the status line, and it fills the same three slots differently: the version, a three digit code, and a short phrase. The code is for the program and the phrase is for the person reading over its shoulder, and the first digit is the whole classification. Two hundreds mean it worked. Three hundreds mean the thing is somewhere else and here is where. Four hundreds mean the client asked for something wrong. Five hundreds mean the server broke while trying. 404 is the number the web gave to chapter three's decision that links are allowed to break: the server is not malfunctioning when it sends one, it is reporting in the ordinary course of business that the thing you named is not here.

One machine, many sites, one header deciding

One header is worth meeting on its own, because it answers something the last chapter left hanging. The path says which file, not which site. Host: says which site, and it exists because one machine at one address serves many of them and has no way of knowing which name you typed. You can prove that in two commands. Both of these go to the same address, ask for the same path, and differ in one line.

One machine, two answers, and the only difference is a name written in a header. The first is a three hundred: this site exists but not at that address, go here instead, and the Location header says where. The second is a four hundred: under that name, there is nothing at this path. The machine did not change. What changed was which of the millions of sites it holds you claimed to be asking for.

Where a message ends, and why that is the hard part

There is one structural problem underneath all of this, and it comes straight from chapter two. TCP delivers an ordered stream of bytes. It does not deliver messages. Nothing in it marks where one thing stops and the next begins, because it has no idea the bytes mean anything. When a program reads from a connection it gets whatever has arrived, which might be half a request, or one request and the first forty bytes of the next. So every protocol built on TCP has to mark its own boundaries, and HTTP does it in two places.

The blank line ends the headers. That is its entire job, which is why it is neither optional nor decoration: a reader consumes lines until it meets an empty one, and then it knows. The length of the body is stated in the headers, usually by Content-Length, giving the exact number of bytes to read.

Sometimes the server does not know the total when it starts sending. Then it uses Transfer-Encoding: chunked and sends the body in pieces, each preceded by its own length in hexadecimal, ending with a piece of length zero. curl --raw declines to tidy that up for you.

22f in hexadecimal is 559, which is the size of that page, and the 0 at the end is the piece that means there are no more pieces. Getting this wrong is the most common way a hand written server breaks, and the server in chapter ten gets it wrong before chapter eleven gets it right.

A real exchange, read line by line

curl speaks HTTP from a command line, and asking it to be verbose makes it print both sides. Lines beginning > are what it sent. Lines beginning < are what came back.

The request is four lines and a blank one. That is the whole of what a client must send to fetch a page, and you could type it yourself, which is what the next chapter does. Two of the response headers are worth stopping on. Server: cloudflare means the machine that answered is not the machine that owns the site. And Age: 14284 says this answer had been sitting in a store for about four hours before it was handed over, while cf-cache-status: HIT says the same thing in different words. Nobody read a file off a disk to answer this request, and chapter fifteen is about why that became necessary.

What came back inside the envelope

Ask for the body rather than throwing it away and you get those 559 bytes: a document in HTML, which is a different agreement from HTTP. HTTP is the envelope and does not care what is inside. HTML is one of the things you can put in it, and Content-Type: text/html is the label on the outside saying which; images, video and machine readable data travel in identical envelopes with different labels. What HTML does is mark up structure rather than appearance, so <h1> says this text is a top level heading and says nothing about what a heading looks like, which is chapter three's fourth decision written down as a format. A third agreement, CSS, covers appearance. The document itself is the next chapter's subject.

One function that reads both halves

Since both messages are text in the same fixed shape, one short function reads either. This one also builds a response, and the builder is the exact function the server in chapter ten uses, so it is worth reading now rather than twice.

Read the two first lines against each other. POST | /search | HTTP/1.1 and HTTP/1.1 | 404 | Not Found are the same three slots holding different things, which is why parse never needed to know which way the message was travelling.

Notice which lines do the work. partition on a blank line separates the headers from everything else. Splitting the first line on spaces gives three fields. Splitting each header on the first colon gives a name and a value. Reading exactly Content-Length bytes gives the body. That is the protocol. A parser used in production adds limits on how long a header may be, careful handling of input designed to break it, support for chunked bodies, and a great deal of attention to malformed text. What it does not add is a different shape.

Check it yourself: two messages in one stream

The claim worth testing is the one about boundaries, because it sounds like a detail. Call show("parsing RAW + RAW:", RAW + RAW) instead, which puts two complete requests back to back in one run of bytes, exactly as they would arrive on a busy connection.

terminal
parsing RAW + RAW:
    first line       POST | /search | HTTP/1.1
    host             example.com
    user-agent       curl/8.7.1
    content-type     application/x-www-form-urlencoded
    content-length   11
    body             b'q=packets\r\n'
    left over        148 bytes

The parsed message is identical. Nothing about the first request changed because a second was stuck to the end of it, and the parser stopped in the right place with 148 bytes remaining, which is the second request untouched and waiting.

Now consider what the parser had to go on. There is no marker in those bytes saying the first message ended. No blank line separates the two, and the second request starts immediately after the last byte of the first body. The only reason the boundary was found is that a header stated a number and the parser believed it. Throw the leftover bytes away and the second visitor is silently ignored. Read too far and you consume the beginning of somebody else's request and both break. Both are real bugs that real servers have shipped, and the first exercise makes you cause them on purpose.

Exercises

  1. predict

    Take two identical requests back to back and change the Content-Length both of them declare. Write down the body and the number of leftover bytes for 11, then 9, then 20, before running anything. Then parse the leftover each time and print the first line the next reader would see.

    At 11 the next reader sees a clean POST | /search | HTTP/1.1. At 9 it sees an empty string, because the two bytes the first message left behind are the line ending, and the stream is now one message out of step. At 20 it sees rch | HTTP/1.1, because the first parse ate nine bytes of the next request. Nothing raised an exception in any of the three. This is the shape of a real and serious attack called request smuggling: get two programs in a chain to disagree by one byte about where a message ended, and you can post your request inside somebody else's.

  2. build

    Write dechunk(rest), which reads a body sent the other way: a length in hexadecimal, then that many bytes, repeated, ending with a length of zero. Return the joined body and whatever came after the final piece.

    Two pieces of 23 and 12 bytes join into 35, and nothing after the zero belongs to this message. Notice what you had to write to get there: the reader is a loop that trusts a stated length, exactly like the Content-Length path, just repeated. Notice also what this buys, because it is the reason it exists at all. A server can start sending before it knows how much there will be, which is how a page is streamed while it is still being produced, and how the token by token output of chapter eighteen's model reaches you.

  3. break

    Send the parser a header line with the colon missing, Content-Length 4, followed by a four byte body. Predict what it does, then decide what a server ought to do instead and write that version.

    It raises nothing. The line becomes a header named content-length 4 with an empty value, so the real length is lost, the body is read as zero bytes, and the four bytes of body are handed to the next reader as if they were a new request. One missing character desynchronised the connection. The fix is not to guess: check the line, and if it cannot be understood, answer 400 Bad Request and close the connection. Being strict about what you accept is not pedantry here, it is the only way the next message stays findable.

in the wild

Open the Network tab in your browser's developer tools and click any request: the headers panel is these exact lines, prettified. fetch() in JavaScript and requests in Python are wrappers that write them for you. HTTP/2 and HTTP/3 carry the same fields in a compressed binary form, which is why curl --http1.1 above was needed to see them as text at all, and why the mental model survives the change. And request smuggling, the thing exercise one produced by accident, is a live vulnerability class precisely because a proxy and a server can disagree about a length.

Where this runs out

We can write a request by hand and we can read a response. What we cannot yet do is anything at all.

where this runs out

Text does not send itself. Something has to open a connection to the right machine, write those exact bytes into it, and read the answer back out. Nothing so far has done that. Then there is the other half: even with the response in hand, we have 559 bytes of angle brackets, and something has to turn <h1> into a large line of text on a screen. That raises a question the format cannot answer for itself. Who decided that <h1> means a heading? HTML is only useful if the program reading it agrees with the program that wrote it, and there is no authority in the bytes to enforce that.

Sending the text, drawing the result, and agreeing on what the marks mean are three jobs. One kind of program does all three, and how it came to be trusted with the third is a stranger story than the other two. That is chapter seven.
