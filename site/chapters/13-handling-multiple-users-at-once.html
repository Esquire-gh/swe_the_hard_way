13 · Handling multiple users at once

Every server you have written answers one visitor at a time. With small local files nobody notices. Put one slow page in front of them and everybody behind it stops. So here is the question every server eventually has to answer: can you handle two users at once? The answer is yes, and the title promises more than one way. This chapter builds the first, measures what it costs, meets the bug it lets in, and then names the other two.

Watching it break

Here is the server from chapter ten with one page that takes a moment to produce.

The sleep stands in for something real: a large file being read off a disk, a wait for another machine, or the database query that arrives in chapter fourteen. It is time during which this request cannot be finished. Ask for the slow page, wait a third of a second, and then ask for the fast one from another window.

The fast page took one and seven tenths of a second, which is the rest of somebody else's two seconds. It did no work of its own worth measuring. Read the loop and the reason is unavoidable. Between accept and the next accept sits everything: reading, handling, writing and closing. The second visitor cannot be accepted until the first is finished, because the line that accepts them is at the top of a loop the program has not come back round to.

The queue you handed to listen does not rescue this, and it helps to see exactly what it does instead. The operating system completes a few connections on your behalf and holds them, so a waiting visitor's browser connects and then sits there, which looks like a blank page rather than an error. When that queue fills, the rest are turned away. Give a server a small queue, never call accept, and send eight visitors at it.

Two get in and wait; the other six are refused. The queue converts one failure, a slow answer, into another, no answer at all. It buys a little time for a burst, and nothing more. The real fix is to stop making people wait for each other.

A second place in the same program

Chapter one described a process as memory, some bookkeeping, and the address of the next instruction to carry out. The last of those is the interesting one here, because nothing says a process may have only one. A thread is a second such place, inside the same process, with its own idea of where it has got to and its own working area for the calls it is inside. Everything else it shares: the same memory, the same variables, the same open descriptors from chapter nine.

The operating system schedules threads the way chapter one described for processes, giving each turns and switching between them thousands of times a second. Making a thread is much cheaper than making a process, because none of the memory has to be set up again. The change to the server is small: take the body of the loop, put it in a function, and start a thread that runs it.

The loop now does one thing: accept somebody and hand them to a thread. It returns to accept at once, so the next visitor waits for the length of one accept call rather than the length of somebody else's request.

One and seven tenths of a second down to six ten thousandths. daemon=True says these threads should not keep the program alive, so control C still stops it; without it, a server with an open connection refuses to exit and you go looking for the reason.

What a thread costs

How many things happen at once is no longer your decision. It is the visitors' decision, and that makes the cost of a thread the ceiling on your server. It is worth measuring rather than guessing. This starts a thousand threads that do nothing but sleep, and reports the memory the process grew by.

A thread is cheap, but not free, and it is cheaper here than the usual figure you will read. Each thread reserves a stack, often close to a megabyte, but reserved memory is not used memory until it is touched, and a sleeping thread touches almost none of it. Even so, the arithmetic decides the ceiling. Ten thousand visitors is ten thousand threads, and at real work rather than sleep the reserved stacks start to matter, so the machine gives out well before the numbers a busy site sees. The two ways past that ceiling are named at the end of this chapter.

The bug you just made possible

Threads share memory. That is what makes them cheap and it is the entire difficulty. Chapter eleven's guestbook kept its messages in a list and its sessions in a dictionary. With one thread, only one piece of code ever touched them. With a thread per visitor, several pieces of code touch them at the same instant, and none knows about the others. The classic failure is any sequence that reads a value, works something out, and writes it back.

the puzzle

The first line is wrong code producing the right answer. Four threads read and wrote a shared number four hundred thousand times with nothing protecting it, and the total came out exactly right. Anybody testing this would ship it. The second line is the same code with one added instruction that does no arithmetic at all, and three quarters of the additions vanished.

What is different between those two lines?

The added instruction is time.sleep(0), which does no arithmetic and offers the scheduler a chance to switch threads at that exact spot. So two threads read the same value, each add one, and each write back the same result. One addition is lost, and that is not something your program controls, observes, or can reproduce on demand. This is a race condition, the shape of every concurrency bug: present the whole time, appearing only when the timing is unlucky, which on a quiet machine may be never and under load may be constantly.

The third line is the fix. A lock is an object only one thread can hold. A thread that asks for a held lock blocks in the sense of chapter eight, using no processor, until the holder gives it back. Wrap the read and the write together and no other thread can get between them. Locks are neither free nor safe by default. Everything inside a lock happens one at a time again, so a lock around too much work removes the point of having threads. And if one thread holds lock A and wants B while another holds B and wants A, both wait forever. That is a deadlock, and the usual defence is a rule that every thread takes locks in the same order. You provoke both of those in the exercises.

One paragraph about Python's threads

One thing is specific to Python and leaving it out would mislead you. In the usual Python, only one thread runs Python instructions at a time, held back by a single lock inside the interpreter called the global interpreter lock. So threads do not give you more arithmetic per second. They still help, because a web server does not spend its time on arithmetic; it spends it waiting, for the network, for a disk, and in chapter fourteen for a database, and a thread that is waiting releases that lock so the others run. That interpreter lock is also why the first line of race.py came out right: it makes single small operations safe by accident, and says nothing about a sequence of them. Most other languages never had one, and there the first line would be wrong too, so code that depends on it is correct for a reason you did not choose.

The three answers the title promised

A thread per visitor is the first and most direct way to serve more than one, and it has the ceiling you just measured. There are two more, and neither is exotic.

The first is to stop letting visitors decide how many threads exist. Keep a fixed number, a thread pool, and hand each new connection to whichever one is free; when they are all busy, the rest wait. The count is yours, so the memory is bounded no matter how many people arrive. The second is to use processes instead of threads, which sidesteps the interpreter lock entirely because each has its own, at the price of not sharing memory. In practice you rarely write either by hand: they are the two numbers you pass a program in chapter sixteen.

The third is different in kind. Instead of many places in the program, have one thread hold every connection, ask the operating system which of them have something ready right now, and do a small piece of work on each in turn. That is an event loop, and it is fifteen lines with the standard library's selectors.

There are no threads here, so there is no race and no lock, and the memory does not grow with the number of visitors. The price is the mirror of the gain: any piece of work that blocks stops everything, because there is only one thread to stop. A single slow database call with no special handling would freeze every connection at once. Getting the speed of the event loop without that trap is what the async machinery in chapter sixteen exists to do, and now you know what it is standing on.

Check it yourself: take the sharing away

The claim that the second line of race.py is about sharing rather than about the arithmetic is checkable with one edit. Change WORKERS from 4 to 1 and run it again.

terminal
$ python3 race.py
no lock                    wanted  100000   got  100000
no lock, switching often   wanted    5000   got    5000
with a lock                wanted    5000   got    5000

Same code, same handing over of turns, same missing lock, and nothing is lost. One thread cannot interleave with itself. The bug was never in the addition.

Exercises

  1. predict

    count_server.py has a page at /count that reads a number, adds one, and writes it back, with no lock. hammer.py sends four hundred requests to it, twenty at a time. Predict the final count before you run them together.

    It comes out short, around 384 on one run here and a different number on the next, because requests that ran at the same instant read the same value and wrote the same value back. This is race.py with the threads created for you by real visitors instead of a for loop, which is the only difference that matters: the bug you saw in a toy is the bug in the guestbook, unchanged.

  2. build

    Fix it, then measure the fix. Uncomment the two lock lines in count_server.py so /count comes out at 400 every time. Then, while the lock is in place, send two requests to /slow at once and time the second one.

    The second /slow finishes in about half a second, its own work, not a whole second, so the two ran at the same time even with the lock in place. The lock wraps only the counter's read and write, and /slow never touches it, so /slow pays nothing. That is the whole craft of locking: hold it around the shared thing and nothing else, so the parts that do not share stay parallel. A lock around the entire request handler would have made this server one-at-a-time again, with extra steps.

  3. break

    Make the deadlock the chapter only described. Two locks, two threads: have one take them in one order and the other in the opposite order, each pausing between the two grabs. Then fix it by making both take them in the same order. deadlock.py is the answer to check against.

    Opposite orders hang forever: each thread holds the lock the other needs and neither will let go. Same order always finishes, because a thread that cannot get the first lock is only waiting, holding nothing, so the other can complete and release. There is no clever detection here and rarely is in practice; the fix is the discipline of a fixed order, which is why real code keeps its locks few and their order written down.

in the wild

The first two answers are two flags. gunicorn --workers 4 --threads 8 starts four processes, each with a pool of eight threads, which is this chapter's processes and thread pool as one command, and the numbers are yours to set from what you measured. The event loop is what uvicorn runs under an async framework. And the race has an answer that is not a lock at all: when the shared counter lives in Redis rather than in your process, INCR does the read, the add and the write as one step nobody can interleave, which is the lock done for you, on the far side of a socket, for every server at once.

What threads cannot fix

The server now serves as many people as the machine can hold, and it is worse off in one respect than it was an hour ago.

where this runs out

Everything it knows still lives in the memory of one process, and chapter one said what happens to that when the process ends. Stop the server and the guestbook is empty and everyone is logged out. What this chapter added is that the same data is now touched by many threads at once, so keeping it correct depends on getting a lock right at every place it is used, forever, including in code written next year by somebody who has not read this chapter.

The data needs to live somewhere that outlives the process, and that place needs to already know what to do when several people touch the same thing at the same moment. Neither is something to build yourself, and the reasons why are chapter fourteen.
