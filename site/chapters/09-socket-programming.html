Part four · building the server

09 · Socket programming and the Linux socket API

The last chapter ended with a request a program has to make to the operating system: make me reachable on this port, take me off the schedule, wake me when somebody arrives, and give me something I can read their text out of and write my answer into. The last part is the interesting one. Whatever comes back has to be something a program can hold, pass around, use later, and have several of at once. It turns out to be a small whole number, the idea is older than networking, and by the end of this chapter you will have written a server and watched the operating system carry out every call it made.

A number that stands for something the program cannot touch

When a program opens a file, the operating system does not hand back the file. It hands back a small whole number. Behind that number it keeps a table, one per process, and each row records what the number refers to, how far through it you have read, and what you are allowed to do with it. Your process holds the number and nothing else. It cannot read the table, edit it, or see anybody else's. Number 3 in your program and number 3 in mine refer to completely different things, and neither program can tell. The number is called a file descriptor.

Three of them exist before your first instruction runs, because the operating system set them up while creating the process. Number 0 is standard input, 1 is standard output, 2 is standard error. When you call print, the text is written to number 1, which is why redirection works: when you type python3 thing.py > out.txt, the shell arranges for descriptor 1 to refer to that file before it starts your program. Your program calls print exactly as it always did and has no idea anything is different.

Everything is a file, which is why this fits

The designers of Unix made that shape the general case rather than a special case for files. A regular file gets a descriptor. So does a named pipe, which is how the last chapter could open one with open and read it like anything else. So does the terminal you are typing into, and so do the devices attached to the machine. All of them are read with the same call and written with the same call, and that call takes a number and does not ask what kind of thing the number refers to.

The numbers are the first lesson. Standard input, output and error took 0, 1 and 2 before the program started. The file took 3. The socket took 4. They came out of one counter, because as far as the operating system is concerned they are one kind of thing.

The last two lines are the second lesson, and they are the whole chapter. os.read was handed a number and asked for 38 bytes. One of those reads came off a disk in this laptop and the other came from a machine in Switzerland, and the call that fetched them is the same call with a different number in it.

Berkeley added the network and kept the shape

In 1983 a research group at the University of California, Berkeley, released a version of Unix with TCP and IP built in, and had to decide what shape networking should have from a program's point of view. They chose the shape that already existed. A network connection would be a file descriptor, and the thing that produces one is called a socket. That design is why the interface you are about to use is the same on macOS, on Linux, and, with the names changed, on Windows.

A connection is not quite a file, so a few calls had to be added. A file has a name, where a socket has an address, a port and a protocol; a file is opened, where a connection is either dialled or answered, and those are different actions. Here are the calls a server makes, in order.

socket asks for a descriptor for talking over a network, connected to nothing yet. bind attaches that descriptor to a particular port on this machine, which is the line from the last chapter about telling the operating system you want to be reachable. listen says that this side answers rather than calls, and from that moment the operating system accepts connections on your behalf and holds them in a short queue even while your program is busy. How long that queue may get is a number you pass in, and it stops mattering only until the day it matters a great deal. accept is the blocking call from the last chapter: it takes the process off the schedule until somebody is in the queue, and then returns.

What accept returns is worth saying loudly, because people carry a wrong picture of it for years. It returns a new descriptor, for that one conversation. The listening socket is never read from and never written to. Its only job is to produce conversations, and it goes straight back to listening. A server therefore has one listening socket and as many connection sockets as it currently has visitors, which is the fact part five is built on. The client side is shorter: socket to get a descriptor, connect to dial an address and port, then read and write, then close.

The first server in this course

Seven calls, in one file, and it answers with whatever you send it.

Three things in those numbers. The listening socket is descriptor 3 in the server and stays 3 forever; the conversation is a different descriptor, handed over by accept, and the server closes it and goes back round. The client's socket is also descriptor 3, on the client, at the same moment, which is the per process table doing its job. And the two clients came from ports 54264 and 54265, which neither of them chose: their operating system picked an unused number when they dialled out.

Everything in chapter ten is this file with one of these lines doing more work. Instead of echoing, it reads the request, works out which file is being asked for, and writes back a response built with the helper from chapter six.

The same calls, as Linux sees them

Python's socket methods are a thin cover over calls the operating system provides, and the covering is close to one for one.

You do not have to take that on trust. strace is a Linux program that reports every request a process makes of the operating system, and -e trace=network keeps only the ones about sockets. This is the server and the client above, in one script, inside a Linux container.

Read the numbers after the equals signs, because they are the descriptors being handed back. socket returned 3, and setsockopt, bind and listen were then told to operate on 3. The client's socket returned 4. And accept4(3, ...) returned 5, which is the claim from two sections ago in the operating system's own words: the call was made on the listening descriptor and produced a different one. The getsockname after it is Python asking which address the new connection ended up on so it can hand you a tidy pair, and nothing in the script asked for it. From that line onward, 3 is never mentioned again. Everything that follows is sendto and recvfrom on 4 and 5, and those two calls are write and read with extra arguments nobody used here.

This interface came from Berkeley Unix and is essentially the same on macOS, where you can read the same manual pages with man 2 socket. Linux's version is the one that matters in practice, because it is what almost every server in the world is running on.

Which conversation is which

There is a question this raises that most explanations skip. A busy machine has a thousand browsers connected to port 443 at the same moment. If a connection were identified by its port, all thousand would be the same connection and the operating system would have no way to tell whose packet was whose.

So a connection is not identified by a port. It is identified by four things together: the address and port at this end, and the address and port at the other end. The server end is the same for everybody and the other end differs, because each client's operating system picks an unused port of its own when it dials out. Four numbers, unique as a group, known as the connection's four tuple.

Three separate conversations with one port on one machine, and the only thing distinguishing them is the number on this end. Two smaller things in that output repay a glance. The descriptors are 3, 6 and 7 rather than 3, 4 and 5, because they are whatever was free at the time and nothing promises they are consecutive. And the address at this end begins 192.168, the private address from chapter four, so this machine is reachable from the internet at no address whatsoever and is still holding three conversations with it.

Check it yourself: one call, three destinations

If a socket really is the same kind of handle, then the call that sent an HTTP request across Europe should also be able to put a line on your screen, because your screen is descriptor 1.

terminal
$ python3 -c "import os; os.write(1, b'this went to standard output\n')"
this went to standard output
$ python3 -c "import os; os.write(1, b'and this went into a file\n')" > /tmp/fd1.txt
$ cat /tmp/fd1.txt
and this went into a file

The same call, with the same number in it, reached a terminal, a file, and earlier a machine in Switzerland. The program contains no code for any of the three cases, and that is not a convenience. It is the reason the seven calls in this chapter needed to add only setup, and why the server in the next chapter can read a browser's request with the same instincts you use on a text file.

Exercises

  1. predict

    Before running same_port.py, write down the three descriptor numbers it will print and the four tuple of each connection. Say which of the eight numbers you can know in advance and which you cannot.

    The addresses and the far port you can know. The three near ports you cannot, because your operating system picks them from whatever is free. And the descriptors are 3, 6 and 7, not 3, 4 and 5, which catches almost everybody: making a connection consumed numbers behind your back, and nothing in the interface ever promised otherwise. Treating a descriptor as anything but an opaque token is the bug this exercise is designed to prevent.

  2. build

    Make the conversation last. The echo server reads once and hangs up; change it so one connection can carry several messages, and have it report the four tuple of each visitor. Write a client that sends three lines down one connection and then closes. The question to answer with your code: how does the server find out the client has gone?

    Your loop ends because recv returns b'', an empty result, and that is the only announcement you get. There is no message that means goodbye. Notice what you have just built and what it costs: while that one conversation is open, the server is inside the inner loop and cannot accept anybody else. A second client will connect and wait, held by the operating system in the queue you gave to listen. That is chapter thirteen's whole problem, arriving three chapters early because you wrote it yourself.

  3. break

    Try to bind a port that is already bound, from a second terminal. Then try to bind port 80 without administrator rights. Predict which line fails in each case before you run it.

    OSError: [Errno 48] Address already in use and PermissionError: [Errno 13] Permission denied, both at bind, before anything is listening and before any client exists. Compare that with the two waiters in chapter five, which both started happily and then fought over files until one crashed. Here the operating system owns the port and refuses the second claim at the door. The privileged range below 1024 is why a real web server on port 80 is started with help and then gives up its privileges, and why every server in this course uses 8000 instead.

in the wild

Every language's networking library is these calls renamed. Go's net.Listen is socket, bind and listen in one; Node's server.listen is the same three; Java's ServerSocket constructor does all three in a constructor. When nginx's configuration says listen 80;, that line becomes a bind and a listen on descriptor 3, and you can watch it happen with the same strace command used above. Nothing above this layer has been invented since 1983, which is why an interface designed for a research Unix is what your cloud bill is ultimately measured in.

Where this runs out

You have written a server. It listens, it blocks, it accepts, it answers, and it goes back round. What it does not do is anything a browser would recognise.

where this runs out

Point a browser at http://127.0.0.1:8000 with echo_server.py running and you will get an error page, because the browser sent a request and got its own request back. Everything needed to fix that is already on the table: chapter six gave the text that goes in and out and a parser for it, chapter eight gave the shape of the loop, and this chapter filled in the line that had no implementation. What is missing is the part in the middle, where the server reads a path, finds a file, and decides what to say when the file is not there.

It fits in one file, and a browser will talk to it. That is chapter ten.
