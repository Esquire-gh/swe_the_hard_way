Part five · more users, more machines

14 · Introducing databases

Every tutorial told you to add a database, and almost none said what one is. Chapters eleven and thirteen both ended in the same place: everything the guestbook knows is in the memory of one process, which dies with it, and is now touched by many threads at once. The data needs somewhere that outlives the process and already knows what to do when several people reach for the same thing. This chapter works out what that somewhere is by trying a file first and watching it fail.

The obvious answer, and it works

Chapter one said a file is a named stretch of bytes on a disk, and that nothing happens inside it while nobody is looking. That inertness is the property we want: write the messages into a file and they are still there tomorrow.

The second run found what the first left. That is persistence, in eleven lines, and for a program with one user it is a perfectly good answer that a great deal of working software is right to use. Notice the shape of add, because everything that follows is about it. Read the whole book. Change it. Write the whole book back.

What it costs the moment anybody else is there

the puzzle

Chapter thirteen ran four threads against a shared number in memory and lost three quarters of the additions, because the threads shared the memory. A file is on a disk. There is no shared variable, each write goes through the operating system, and the file is complete and valid between runs.

Run the same four threads against this file. What, if anything, goes wrong?

lost_and_truncated.py keeps the same add from above and runs four writers at it. The only change is that when a read fails, it counts it rather than crashing.

Your numbers will differ, and the three failures will not. A reader can catch the file between the old contents and the new: a hundred and seventy five attempts out of two hundred opened it partway through somebody else's write and got something invalid. In this program they gave up; in a web server they are an error page for a visitor who did nothing wrong. The file that survives is broken, because two writers wrote over each other, so it is not that messages were lost, it is that the file cannot be read at all. And a write can be interrupted: opening a file for writing empties it first, before a single new byte is written, so a power cut at that instant does not lose the last message, it loses the guestbook.

There is a third cost, met on a good day rather than a bad one. Finding one record among many, in a file, means reading every record before it.

Ten times the records, ten times the time, because find_in_file reads to the end. The right hand column barely moves. Whatever the database is doing, it is not looking at a million things to find one.

Everything you would build next already exists

The answers are all within reach, and worth naming quickly so you feel their weight rather than being handed a product. Stop writing in place: write a new file and rename it over the old one, so a reader sees old or new and never a mixture. Take a lock so two writers cannot overlap, and decide what happens when the holder dies. Stop rewriting the whole file: append what changed and fold the changes back in the background. Keep a second, sorted structure mapping each id to a position, and keep it correct on every write, including the ones that fail halfway. Together, these are a database: a program that keeps records on a disk in a layout designed around exactly these problems, attacked by more people over more years than your version ever will be.

A language for saying what, not how

Databases are driven by a language built for one subject rather than for general computation, a domain specific language, and this one is called SQL. The property that matters is that you say what you want and not how to get it.

SELECT who, text FROM messages WHERE id = 5

Nothing there says whether to use an index or read every row. The database decides, and decides differently as the table grows, without the sentence changing. The file version had the how baked into code you wrote, and it would scan the whole file until somebody rewrote it.

The guestbook, kept properly

guestbook_db.py uses sqlite3, which is in Python's standard library, so this chapter installs nothing. Each connection opens with two lines that are doing more than they show.

The timeout says a writer that finds the database busy should wait up to ten seconds rather than fail at once. WAL, the write ahead log, is a journal that lets readers keep reading while a writer writes. Those two lines are the whole reason the next test works, and the break exercise takes them out so you can see what they were holding up. First the shape of a message is written down, then the same test as before: four threads, fifty messages each.

Two hundred out of two hundred, and you did not write a lock. Making concurrent writers correct is the database's job, the same job chapter thirteen handed to you, done once by people who spent years on it. Three things in that setup carry more weight than they look. NOT NULL means a message with no author cannot be stored, where the file let one through to fail a page later. The shape a table enforces is its schema. CREATE INDEX builds the second, sorted structure from the last section and keeps it correct on every write. And commit marks the end of a transaction, a group of changes that either all happen or none do, which is the answer to the truncated file applied at every level. Those properties are usually quoted by their initials, ACID: all or nothing, always valid, never half visible to others, and safe once confirmed.

More than one table, and the word "relational"

The guestbook wrote the author's name into every message. Put the same name in a thousand messages and you have stored it a thousand times, and the day somebody renames themselves you must find and fix all thousand. The fix is to keep people in one table and messages in another, and have each message point at a person by id. Following that pointer is a join, and it is where the word relational comes from.

The name lives in exactly one place, so the rename touched one row and every message reflected it. REFERENCES people (id) also means the database will refuse a message whose author does not exist, which is another whole class of broken data that cannot occur rather than being caught later. The join is the database doing, in one sentence you did not have to optimise, the cross referencing you would otherwise write and rewrite by hand.

What the schema is worth, measured

A schema is not paperwork. It refuses bad data, it undoes a group of changes that cannot all succeed, and it charges you for the index that makes reads fast. All three are visible in a few lines.

The rolled back transaction is the one to sit with. Grace was inserted successfully, and then a second insert in the same transaction failed, and the database undid the good insert along with the bad one, because a transaction is a unit. That is exactly what you want when the two inserts are "take money from one account" and "add it to another", and it is why moving money is a transaction and not two writes. The index tax is the other side of the ledger: the fast reads from earlier are bought with writes that here ran more than twice as slow, which is why an index on every column is a common and expensive mistake.

The same bug, a third time

One danger arrives with SQL and it is one you have already met twice. If you build a query by pasting a name from a stranger into the text, a name containing a quote can close the string and turn the rest into part of the query, returning every row or worse. This is SQL injection, and it is chapter ten's path traversal and chapter eleven's cross site scripting wearing new clothes: text from outside placed where the program keeps its own instructions. The fix is the same shape too. Do not build the instruction out of the text; leave a slot, the ?, and hand the text over as a value, which every query in this chapter already does.

The server in front, and why it is there

One thing here is not like a real deployment. sqlite3 is a library: your process opens the file and reads it directly, with no other program involved, which is why this chapter installed nothing. The usual arrangement is a separate program that owns the files and lets nobody else near them, which your program connects to over a socket, exactly as chapter nine described, on its own port, speaking its own protocol that is not HTTP. Everything from chapter five applies: the database server was started first, it waits, and your application is the client. The reason for the extra program is chapter seventeen arriving early. When your application runs on eight machines, they cannot all open the same file on one disk, but they can all connect to one program. A database is that program, usually with a server in front, driven by a language built for one purpose. SQLite is the same thing with the server left out.

Check it yourself: ask the database what it plans to do

The claim that SQL says what rather than how is checkable, because you can ask what it decided. plan.py asks the same question twice, before and after creating an index.

terminal
$ python3 plan.py
with no index on who:
    SCAN messages

after adding one:
    SEARCH messages USING INDEX messages_by_who (who=?)

The question was identical both times. The only change was that a second structure appeared on the disk, and the database noticed and changed its mind. SCAN is the file version from earlier, reading everything. SEARCH is the fast column in that table. Nobody edited a query, and the program got faster.

Exercises

  1. predict

    A program inserts messages one at a time and is killed dead, with kill -9, partway through. Predict how many survive in two versions: one that commits after every insert, and one that commits only at the very end. Then run kill_survival.py.

    Committing each insert, whatever was written before the kill survives, around a hundred and sixty here. Committing only at the end, nothing survives, not even the table in one run, because none of it was ever made durable. This is the exact meaning of the D in ACID: a commit is a promise that a power cut cannot break, and a write with no commit is a note in memory that dies with the process, which is the state every program in chapters eleven and thirteen was permanently in.

  2. build

    Fix the file by hand, without a database, until it survives the four writers. Write each new version to a temporary file and os.replace it over the old one, so a reader never sees a half written file, and take a lock so two writers cannot overlap. Get fixed.json to two hundred of two hundred.

    Both fixes are a few lines, and fixed_file.py reaches 200 of 200. Now look at what you have built: a lock, an atomic replace, and the beginnings of the story about the holder dying mid-write. You have re-derived, by hand, two of the four things that make a database, and you have not yet touched the index, the transaction across several files, or the server in front. This is the exercise that makes "just use a database" stop sounding like laziness.

  3. break

    Take away the two lines from connect. Open the database with timeout=0 and no WAL, run the same four writers, and count how many are turned away. Predict the error first.

    sqlite3.OperationalError: database is locked, well over a hundred times, with only a handful of messages stored. The concurrency you took for granted two sections ago was those two lines, not magic: the database made letting writers overlap a policy you switch on, with a cost, rather than a problem that vanished. Every managed database has the same switches under grander names, and knowing they are switches is the difference between tuning one and being frightened of it.

in the wild

Everything here has a bigger name. Postgres on port 5432 and MySQL on 3306 are this chapter with the server in front, so your code connects over a socket instead of opening a file, and the SQL barely changes. EXPLAIN QUERY PLAN is EXPLAIN ANALYZE in Postgres, the same question about how the database will answer, and reading it is most of what performance work turns out to be. And an ORM, the layer many frameworks put on top, is this SQL with method names: Message.objects.filter(who="Ada") becomes the SELECT you already know, which is worth remembering the first time one produces a query that reads a million rows.

Now make it popular

Here is what exists now: a server that answers many people at once, running your code for each, with data that survives the process being stopped and stays correct while several visitors write at the same moment. Everything up to this point has been about making it work at all.

where this runs out

Everything after it is about a different problem, which is that it works and then a lot of people arrive. The machine runs out of room for visitors, some piece of work takes longer than anybody will wait for, the same expensive answer is computed thousands of times a second, and putting a new version on the machine means stopping the old one and going dark while you do.

Each of those has an answer, each answer is a word you have heard, and the words are far easier to remember once you have felt the thing they fix. That is chapter fifteen.
