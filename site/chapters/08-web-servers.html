Part four · building the server

08 · Web servers

Chapter five measured a server doing nothing and found it costing 0.4 per cent of a processor, and the last chapter had you talk to one that has been running since 2014. So what is it doing all day? Written out in ordinary words, a web server is six lines, and five of them you could write today. The sixth says wait, and it has no obvious implementation at all, because a processor has no instruction that means pause here until a stranger somewhere in the world decides to connect. This chapter is about that line.

The shape of every server ever written

Start with the whole thing, because it is short. A web server is a program that is started once and left running, and what it does for the rest of its life is this.

tell the operating system you want to be reachable
forever:
    wait until somebody connects
    read the text they sent
    work out what they are asking for
    write the answer back
    close the connection

That is not a simplification of a web server. That is a web server. The one you write in chapter ten has this shape, and so do the large ones running most of the internet. What separates them is how much happens inside the line about working out what they are asking for, and how many of these loops run at the same time, which is the question part five opens with.

The words for the parts are worth having. A program that is started once and stays up is a long running process. A server that has told the operating system it wants to be reachable, and is now waiting, is listening. The loop itself, one visitor in and one answer out and around again, is the accept loop, and a single trip through it is what people mean by the request response cycle.

Ask which of the six you could write now. Reading text and writing text you have done since your first program. Working out what the request means is the last chapter but one, and it came to thirty lines. Closing something when you have finished is ordinary. Telling the operating system that you want to be reachable is a request you do not yet know how to make, but you can at least see that it is a request. That leaves one line with nothing behind it, and it is the second one.

What waiting means for a program

the puzzle

A process is a sequence of instructions carried out one at a time by a processor, and a processor knows only a few dozen kinds of instruction: move this, add that, jump there. A server spends nearly all of its life waiting, and the one in the last chapter answered within a few hundredths of a second of the request arriving.

So which instruction is "wait"? And if the server is running no instructions while it waits, what noticed that you had arrived?

Two ways to wait, and only one of them is free

There are exactly two ways for a program to wait for something, and the difference between them matters more than it sounds.

The first is to keep asking. Look for the thing, and if it is not there, wait a moment and look again. The waiting program in chapter five did this, twenty times a second, all day. This is called polling. It works, and it has two costs that pull against each other. The processor does work every time it looks, including on all the occasions when there is nothing there. And there is a delay between the moment something arrives and the moment the program notices, of up to one full gap. Shorten the gap to reduce the delay and you increase the waste; lengthen it to reduce the waste and you increase the delay. There is no setting that is good, only settings that are wrong in different proportions, which the second exercise makes you measure.

The second way is to hand the problem to the operating system. The program says what it is waiting for and then stops. The operating system takes the process off the schedule entirely, so it is no longer offered turns on a processor. When the thing arrives, the operating system puts the process back on the schedule and it carries on from the instruction after the one that stopped. Between those two moments the process runs no instructions at all. This is called blocking, and a process waiting this way is described as blocked.

Measuring the difference

We cannot wait on a network connection yet, because that is chapter nine. So wait on something we already understand. A named pipe is a thing that looks like a file and has no disk behind it: one program writes into it, another reads out of it, and the bytes go straight from one to the other through memory. It appears in a directory listing with a p at the front where an ordinary file has a dash.

What matters is that opening one for reading does not return until somebody opens the other end for writing. It is a thing you can block on, and it is a fair stand in for the real case: a connection arriving at a port is the same situation, a thing that is not there yet, and the mechanism the next chapter reaches for is the same mechanism. Here are the two ways of waiting, doing the same job. First the one that keeps looking.

Then the one that stops.

time.perf_counter measures time passing in the world. time.process_time measures processor time given to this process, which is the number that matters. Start one of them, count to ten, then knock from a second window with knock.py.

Both waited the same ten seconds and both got the message. One asked 1,632 times and was wrong 1,631 times. The other asked once.

Two hundred of them

Forty six thousandths of a second sounds like nothing, and for one program it is. A machine does not run one program. Start two hundred processes that all wait the same way, leave them for ten seconds, then add up the processor time they used between them.

Nine and a third seconds of processor time in ten and a half seconds of clock time. That is close enough to one entire processor, running flat out, to discover that nothing has happened. The blocking crowd cost five hundredths of a second between all two hundred of them, most of which was starting up. Neither crowd did anything useful, and one of them was paid for.

The cost also scales the wrong way with attentiveness. Halve the gap between looks and the count doubles, the cost doubles, and the program is no more useful than it was; the machine notices slightly sooner.

Check it yourself: look at the process while it waits

Start blocking.py and leave it. In another window, ask the operating system what it thinks of that process.

terminal two
$ ps -o pid,stat,%cpu,command -p 71243
  PID STAT  %CPU COMMAND
71243 SN     0.0 python3 blocking.py

S and 0.0. The operating system's own record says this process is not runnable. It is not being offered turns, it is not looking at anything, and it is not, in any sense the machine recognises, doing something. That would be surprising if blocking were a clever kind of fast polling. It is not. The process really has stopped, and the reason it wakes at the right moment has nothing to do with the process.

if ps says no such process

The number is the process id blocking.py got on the author's machine. Yours is different; find it with pgrep -f blocking.py.

Exercises

  1. predict

    Before running anything, write down the processor time polling.py would use over ten seconds at three settings: a gap of 1 millisecond, 5 milliseconds, and 50 milliseconds. Then write down how late each one would notice a message on average.

    The cost goes up roughly as the gap comes down, and the lateness goes down with it, in almost exactly the same proportion. There is nothing subtle here and that is the point: you are buying attentiveness with processor time at a fixed exchange rate, and no amount of care in choosing the number changes the rate. Anyone who has tuned a polling interval in a real system has had this argument with themselves.

  2. build

    Measure it rather than reasoning about it. Sweep the gap across 1, 5, 50 and 200 milliseconds, and for each one record two numbers: the processor time spent looking, and how long the message actually sat there before it was noticed. To get the second number honestly, have the writer stamp the moment it wrote.

    A clean, boring table: 1 millisecond costs about twelve times what 200 milliseconds costs and notices about two hundred times sooner. Every row is a defensible engineering decision and none of them is good. Keep the table. The next chapter deletes the whole trade, and the table is what makes that feel like a relief rather than a detail.

  3. break

    Start two hundred pollers at once, wait ten seconds, wake them all, and add up the processor time they used between them. Then do the same with two hundred blockers.

    Nine and a third seconds against five hundredths: one processor core against nothing. Two things follow. Polling does not fail gradually, it fails by multiplication, so the arithmetic that was fine in development is a burning machine in production. And a server that blocks can hold far more idle connections than one that polls, which is why the number of visitors a machine can keep waiting is a different question from how fast it answers any of them.

in the wild

Blocking on one thing at a time is not what a real server does, because it has thousands of connections open and needs to be woken by whichever of them speaks next. The operating system provides exactly that: epoll on Linux, kqueue on the systems macOS came from. One call, a list of things to watch, and the process sleeps until any of them is ready. That call is what nginx, Node and every asynchronous framework are built on, and the loop around it is what chapter thirteen calls an event loop. The idea is the one in this chapter, and only the number of things being waited for has changed.

Where this runs out

We now know what the missing line in the server loop has to mean: stop this process, and start it again when somebody connects. There are two reasons a program cannot carry that out itself.

The first is that a stopped process is stopped. Somebody has to be running at the moment the connection arrives, to notice it and put the process back on the schedule, and that somebody cannot be the process. Whoever does the waking is never the one asleep. The second is that the thing being waited for is a piece of hardware. The bytes arrive at a network card, and the operating system owns the devices for the same reason it hands out turns on the processor. A process cannot read the network card directly, any more than it can read another process's memory. If it could, every program on your laptop could read every other program's traffic.

where this runs out

So the line has to become a request to the operating system: I want to be reachable on this port, wake me when somebody arrives, and take me off the schedule until then. A request like that has to give something back. The program needs to hold on to whatever arrives, read the visitor's text out of it, and write an answer into it, possibly for a long time and possibly while other things are going on. The bookkeeping the operating system already keeps for a process includes the list of files it has open, and the people who designed this noticed that a program which can read from and write to an open file would need to learn almost nothing to read from and write to a connection, if the connection were handed over in the same shape.

That handle has a name, and chapter nine is about what it is, what the operating system is doing behind it, and how to make the request in seven calls.
