Part five · more users, more machines

18 · AI systems are still software

The way people write about machine learning suggests a separate discipline, with its own vocabulary and its own conferences, and a habit of describing systems in terms that sound like nothing else in software. The question for this chapter is narrow. Set aside what a model is and what it does, which is a different subject and a good one. Ask only about the engineering. When a model is trained, what is running, and where? When you send it a question and words come back, what happened between those two moments? The answer is this course again, the same things with different words on them, and the chapter teaches nothing new on purpose. If it works, the feeling by the end is recognition.

Training is chapter one, with the numbers changed

Training a model is a program running on a computer. There is a file on a disk, or a great many of them, holding the data. A process is created, in the sense of chapter one, and the operating system gives it memory and schedules it. It reads a portion of the data off the disk, does a large amount of arithmetic, adjusts some numbers it is holding, and does it again. Millions of times.

The arithmetic runs on a graphics processor rather than the one chapter one described, and the difference is one of shape rather than of kind. A GPU has thousands of simpler processors that all perform the same operation on different numbers at the same moment, which suits arithmetic on very large grids of numbers. Chapter one's fetch, do, advance loop is what each of them is doing. There are just a great many of them, and everything else in chapter one applies unchanged. The process has an id, it can be listed with ps, and it uses memory the operating system gave it, which is gone when the process exits.

That last fact is why a training run writes its numbers to a disk from time to time. The saved copy is a checkpoint, and it exists for the reason chapter fourteen gave: a process's memory does not survive the process, so anything that must outlive a crash has to be written down. You can watch the whole cycle in one run. checkpoint.py counts steps, writes the count to a file every third step, is killed partway through, and is started again by a stand-in supervisor.

Step seven happens twice. The process that died had done it and lost it, because its memory did not survive it; the file on disk did survive, so the restart repeats only the work since the last write. That is chapter fourteen's durability and chapter fifteen's supervisor together, and the industry calls the combination fault tolerant training. There is a subtler inheritance from chapter fifteen too. Those thousands of processors are expensive and sit idle if the data does not arrive fast enough, so a large part of the work is reading files off disks quickly and getting them into the right memory: one slow component holding up everything in front of it.

Training is also chapter seventeen

A model too large for one machine, or a run that would take a year on one, is spread across many, and then every sentence in chapter seventeen applies. The usual arrangement gives each machine a copy of the numbers and a different portion of the data. Each does its arithmetic, and then all of them combine their adjustments before the next step, because otherwise they would drift into being different models. That combining step is a point where every machine waits for every other one.

The three fast workers spend three quarters of a second doing nothing, every step, waiting at the barrier for the slow one. The slowest machine sets the pace for all of them, which is exactly why chapter seventeen said a machine that has gone slow is worse than one that has died: the dead one is noticed and replaced, while the slow one just holds the line. When the model itself is too large for one machine's memory it is cut up and the pieces placed on different machines, which is chapter seventeen's sharding with the same costs, and the network between the pieces becomes the limit rather than the arithmetic. None of that is specific to models. It is what happens whenever a computation is split across machines that must agree on a shared result at every step.

A model that answers is chapter five's server

Training produces a large file of numbers. Using it is a different program with a completely familiar shape. A process starts on a machine, loads that file into memory, opens a socket, binds a port, listens, and waits, which is chapters eight and nine with no modification. It is a server in exactly chapter five's sense: it was running before you arrived, it does not know you exist until you connect, and it cannot start the conversation.

There is one honest difference, and it is in the starting rather than the answering. big_load.py makes it visible: the server reads its weights off the disk into memory before it will answer anything, and a large model is a large file.

The reply costs the same tiny amount whatever the file size; the wait to start grows with it. Real weights are tens or hundreds of gigabytes, so a server takes minutes to come up, and that single fact shapes how these services are deployed, which the last section returns to.

Your request travels there as chapter six described: a request line, headers with your credentials among them, a blank line, and a body, which for these servers is usually JSON. The answer comes back as a status line, headers, a blank line, and a body. If you have an API key you can send that request with nc and read the reply, and there is nothing in it chapter six did not cover. The tokens everybody counts are just the pieces your text is cut into before the model reads it, a unit of counting that changes nothing about the machinery here.

Why the words appear one at a time

The one visible difference between a chat window and an ordinary web page is that the answer arrives gradually. That looks like a new capability and it is chapter six. stream.py is a server that sends a sentence one word at a time, and a client that prints each piece as it arrives with the time it turned up.

That is Transfer-Encoding: chunked, which chapter six met on a response from example.com: the way a server sends a body whose total length it does not know when it starts. Each line is a length in hexadecimal, then that many bytes, then the next one, ending with a length of zero. A program producing text a piece at a time does not know the total length in advance, so it uses the mechanism that already existed for that. Real services wrap each piece as a data: line in a format called Server-Sent Events, but the transport underneath is exactly this. The connection stays open for the whole answer, which is why chapters thirteen and seventeen matter so much for these services: one conversation holds a slot for as long as it takes, and how long that is cannot be known in advance.

Chapter fifteen, unchanged, with new names

Everything that surrounds one of these servers in production is chapter fifteen. Requests arrive faster than the expensive hardware can take them, so they go into a queue and wait, which is why these services have rate limits and why a busy one tells you to try again later. That is backpressure, and refusing quickly is kinder than accepting and never answering. The hardware is also far more efficient doing many requests together than one at a time, so the server deliberately waits a moment to collect several and runs them as a group.

One forward pass costs about the same whether it carries one request or eight, so grouping them does eight times the work in the same time. That is a queue with an intentional delay, trading a little latency for a lot of throughput, and the version that lets a new request join a group already in progress is called continuous batching. While answering, the model reuses results it computed for earlier parts of the same conversation, and keeping those rather than recomputing them is a cache in chapter fifteen's sense. It lives in the expensive memory next to the processors, which makes it the main limit on how many conversations one machine can hold, and when that memory fills something has to be thrown away: cache eviction, with the same trade as always. When many requests begin with the same long piece of text, the work of processing that prefix is kept and reused, which the providers call prompt caching, the cf-cache-status: HIT header from chapter six one layer down. A request that times out may have been completed and billed, so a client that retries needs chapter seventeen's idempotency key to let the server recognise a repeat.

What is genuinely different

Three things, and it is worth being exact, because pretending nothing is different would be as wrong as pretending everything is. First, the work per request is enormous and its size cannot be known before it starts. An ordinary page takes about as long every time; here the cost depends on how much text comes back, decided while the answer is produced. That makes every timeout in chapter seventeen and every capacity estimate in chapter fifteen harder, because the thing being estimated is genuinely unknown at the moment you must estimate it. Second, the same input need not produce the same output. A database read is a function of what is stored; these servers usually choose among possibilities as they go, so two identical requests can return different text. That does not break caching, but it makes caching a decision about behaviour rather than an invisible optimisation. Third, the file of numbers is very large, which big_load.py showed: starting a process means loading tens or hundreds of gigabytes before it can answer, so chapter fifteen's trick of starting the new version before stopping the old one is expensive here in a way it is not for a web application, and deployment for these services is shaped almost entirely by that one fact.

Notice what is not on that list. Nothing about how the requests arrive, how the server waits, how the data is stored, how the machines coordinate, or how the whole thing is deployed and watched. An agent, while we are here, is a client. It is a program that makes HTTP requests to a model server, reads the answer, and on the strength of it makes further requests to other servers, with retries and timeouts and idempotency keys. Chapters five through seventeen describe it completely.

Check it yourself: read the pieces

Run stream.py and look at the fourth line of output.

terminal
 0.32s  b'a\r\nanswering \r\n'

The a is a length written in hexadecimal, so it is ten, and answering is ten bytes including its trailing space. That is the framing chapter six described, arriving from a program you wrote, over a socket you opened, a third of a second after the previous piece. Nothing about that line is about models. It is a length, some bytes, and a line ending, and when you next watch an answer appear a few words at a time in a browser, that is what is happening underneath.

Exercises

  1. predict

    Take the sentence stream.py sends and work out, by hand, the column of chunk lengths it will print, in hexadecimal. Remember each word carries a trailing space. Then run hex_lengths.py to check every line at once.

    The lengths are 2, 6, a, 3, 2, 7, 8, 5, 5, 2, 7, and the one that trips people is answering at ten bytes, written a and not 10 because the count is in hexadecimal. That is all "chunked" means as a wire format: each piece announces its own byte length and the reader takes exactly that many. You have read the framing a streaming AI answer arrives in, and there was no model in it, only a number, some bytes, and a line ending.

  2. build

    Build the agent. A client that asks a model server what to do, reads the action it names, and carries it out by calling a second server, retrying on a timeout with one idempotency key so the action lands exactly once. Stub both servers in-process so the whole thing runs on its own.

    agent.py ends with the guestbook holding one row even though the first attempt timed out. Read what it is: a loop that makes an HTTP request, reads the reply, and makes another on the strength of it, with chapter seventeen's idempotency key across the retries. There is no new idea in the file. An agent is a client, and the intelligence is on the far end of a socket, behind this chapter's queue and cache. When the word starts to sound like magic, this file is what is underneath it.

  3. break

    A streamed answer holds the connection open, so a client with a timeout can give up in the middle, after the server has already charged the card at the start. Write that: a server that charges and then streams slowly, and a client that times out and retries. Predict how many times it charges before you run double_charge.py.

    Twice without an idempotency key, once with one. Streaming makes it sharper than chapter seventeen's version: the charge happens up front and the answer dribbles out after, so the window in which a client can give up already charged is the whole length of the answer, which here is long and of unknown size. The fix is the same, one key across the retries, but it matters more because the thing holding the connection open is the thing this chapter is about.

in the wild

Each idea here has a name in production. vLLM is the batching and the reused attention cache from the pressures section, written as a serving engine and measured in the tokens per second it gets out of one GPU. The 429 Too Many Requests you hit on a busy API is the queue refusing you on purpose, with a Retry-After header telling you when to come back. And the chat window streaming a reply a few words at a time is a browser running fetch() and reading the response body in chunks as they arrive, the same chunked encoding stream.py printed, rendered into a growing paragraph instead of a terminal.

One thing left

Everything in this chapter that arrived wearing a new word turned out to be something you had already built: a process with a checkpoint, a barrier, a server loading a file, a chunked stream, a queue with a cache in front of it. There is one thing left to do with all of it.

The last page follows a single request from a typed address to a drawn page, all the way down, with nothing left as something that just happens. It is the promise this course opened with.
