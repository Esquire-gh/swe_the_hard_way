Part four · building the server

12 · Servers as hardware and software

You now have two programs, and the same word is used for both. One reads files off a disk and sends them back. One runs your code to produce the answer. You are also sitting at a laptop that is answering HTTP requests, and nobody would call a laptop a server. The word is doing at least three jobs at once, and mixing them up makes most writing about this subject harder to read than it needs to be. This chapter sorts the word out, and it takes about five minutes.

The two things the word means

A server in the sense chapter five defined is a program. It waits, it accepts connections, it answers, and it goes back to waiting. That is a role a process plays, and any machine can run one. server_safe.py is a server in this sense, and so is step4_session.py.

A server in the other sense is a physical computer, and specifically one built for running programs like that without stopping. It usually has no screen or keyboard, it is shaped to slide into a rack, it has more memory and more processors than a desktop, often two power supplies in case one fails, memory that can detect and correct its own errors, and some way to be restarted by somebody who is not in the building.

The two meanings share a word for a dull historical reason. For a long time, if you ran server programs you bought a machine specifically to do it, and nothing else ran on that machine. Naming the box after its job was reasonable, because the box had one job. That is no longer true in either direction, and both directions are worth seeing.

One machine, many servers

Chapter five had you list the programs on your laptop that were in the waiting state, and there were more than you expected. Here is that list again while the proxy and backend from later in this chapter are both running.

Four servers, one laptop. Two of them are your own Python processes, each holding one port. The other two are a database and a cache, and they are worth a second look, because they share one process id. That single com.docker process is holding both ports, and behind it are two containers, which chapter fifteen will use in earnest. A container is not a machine. It is ordinary processes on this laptop, as described in chapter one, given a restricted view of the filesystem and the network so they behave as though they were alone. From the operating system's side, seen through lsof, a container is what you are looking at: a process holding a port. The mystery is mostly in the naming.

The machine underneath may also not be a machine. When you rent a server today you are usually given a virtual machine, which is a computer implemented in software on top of a real one, convinced it has hardware of its own, and one physical box runs several of them for customers who have never met. This is enough to stop the words being frightening; the details wait until you need them.

One server, many machines

It runs the other way too. The thing people call "the Wikipedia server" is a large number of computers in several countries, and chapter four already showed you one name resolving to several addresses. The practical value of keeping the two meanings apart shows up when something breaks. "The server is down" can mean the building lost power, or that the machine is perfectly fine and your process exited four minutes ago, which you watched happen at the end of chapter eleven. Those have nothing in common except the sentence.

The other split, and a program that shows it

There is a second overloading inside the software meaning, and you have written one of each. A program whose job is to read files off a disk and send them back, speaking HTTP, is a web server in the narrow sense; nginx and Apache are the two everybody has heard of, and they are your file server with thirty years of work on top. A program that stops reading files and runs your code to produce the answer is an application server; the FastAPI program in chapter sixteen is one.

In production both are usually present at once, and the way they are joined is a program simple enough to write here. A reverse proxy holds the port the outside world connects to, and for each connection opens a second socket to the application server behind it and relays the bytes both ways. The visitor thinks it is talking to one server. It is talking to two, and the front one chose which.

Run the guestbook on 8001 and this on 8000, and a visitor asking the proxy is answered by the backend without ever connecting to it.

Read the backend's log. The client it recorded is 127.0.0.1, the proxy, not whoever ran curl. From the backend's side the proxy is the visitor, which is exactly the property that makes this useful. The front program can hold thousands of slow connections, serve the files that never change, handle encryption, and pass only the real work to the back. It can also go on answering while the back one is restarted, which is the whole of the zero downtime deploy chapter fifteen builds on top of this same file.

Check it yourself: one machine, many servers, one port each

The claim that a machine can hold any number of servers, but that a port holds one, is checkable in fifteen lines.

terminal
$ python3 two_at_one_port.py
claimed port 8200
claimed port 8201 as well, on the same machine
asking for port 8200 again: Address already in use

One process here holds two ports, and a machine could hold thousands. The third attempt is refused, and the refusal comes from the operating system rather than from any agreement between programs. Chapter nine explained why: the port is how the operating system decides which waiting program an arriving connection belongs to, so allowing two claims on one number would leave it with a question it could not answer.

if it fails on the first call instead of the third

One of those numbers is already taken on your machine. That is the same message telling you the same thing, and picking a different number fixes it. Ports being occupied by things you forgot you installed is a normal part of this work.

Exercises

  1. predict

    One program binds 0.0.0.0:8000 and another binds 127.0.0.1:8000. They are different addresses, so do they both succeed? Write your answer down before running two_addresses.py.

    They collide, and the second one is refused. 0.0.0.0 does not mean one address; it means every address this machine has, and 127.0.0.1 is one of them, so the first bind already owns the second's port. The rule from the check still holds, you were just reading the addresses as if they did not overlap. Two genuinely different addresses, two real network cards, could each hold port 8000, which is how one machine serves two networks on the same number.

  2. build

    Build the reverse proxy above from scratch before reading it closely. Hold one port, connect to another, and relay bytes both ways. The relaying is the part that repays thought: a connection has two directions, and each ends at a different time, so you cannot copy one way and then the other. Run any backend behind it and confirm the backend sees the proxy as its client.

    The two directions are why the listing starts a thread for one way and runs the other on the current one. Copy visitor to backend to completion first and you would never start sending the answer back, because the visitor has not hung up. This is the same one-thing-at-a-time limit as chapter eight, met from the other side: two independent streams need two flows of control, and a thread is the cheapest one to reach for. That is chapter thirteen arriving early again.

  3. break

    The check says a port holds one program. Break it on purpose. Set SO_REUSEPORT on two sockets and bind both to the same port, and predict what happens before you run reuseport.py.

    Both binds succeed. One port, two programs, and the kernel hands each new connection to one of them. The rule was never physics; it was a policy the operating system enforces by default and will drop when you ask, precisely so a server can run several identical worker processes behind one port with nothing in front of them. Knowing which of your certainties are laws and which are switches somebody chose is most of what separates fixing a system from guessing at it.

in the wild

The arrangement in this chapter has a standard shape and two standard names. nginx in front is the reverse proxy you wrote, grown up: it terminates encryption, serves static files, and holds the connections. gunicorn or uWSGI behind it is the application server running your code, and the pair is described as "nginx in front of gunicorn" so often it sounds like one word. When a cloud platform says it gives you a container, the process it starts is the back half of this picture, and its own load balancer is the front half, which is why you so rarely have to write either by hand. You have now written both.

Naming things does not add capability

The words are sorted out, which is worth something, and the programs are exactly as capable as they were.

where this runs out

Both of them still answer one visitor at a time. The loop accepts a connection, deals with it from start to finish, and only then goes back to accept. With small pages on your own laptop nobody can tell. The first time a request takes a while, everybody behind it finds out. The proxy you just wrote is the one exception, and only because it reached for a thread, which was a hint.

Part five opens with the question every server eventually has to answer: can you handle two users at once? That is chapter thirteen.
