Part three · the conversation

07 · Web browsers

The browser is the program you use most and think about least. The last chapter finished with three jobs and nothing doing any of them: the request has to be sent, the response has to be turned into something a person can look at, and somebody has to have decided what <h1> means, or the whole arrangement is two programs exchanging punctuation. One kind of program does all three, and it is larger than most operating systems were when the web was invented. The way to find out what all of it is for is to do the jobs yourself and see which ones you can finish.

A program that joins two points and stays out of the way

To send the text from the last chapter you need something that opens a connection to another machine and then gets out of the way. nc, short for netcat, is that. It connects, copies whatever you give it into the connection, and prints whatever comes back. It knows nothing about HTTP and has no opinion about what you send. It is a pipe with a network on one end.

It needs two things: which machine, and which of the waiting programs on that machine. That second one has been in the background since chapter five and is worth naming now. A machine runs many waiting programs at once, which you saw in the LISTEN listing, so an address alone cannot say who you mean. Every waiting program claims a number, every packet carries the number it is for, and the operating system uses it to decide which program a new connection belongs to. The number is a port. Chapter nine is about the mechanism; for now, the web agreed long ago that plain HTTP lives on port 80 and encrypted HTTP on port 443, which is why you have never had to type either.

Job one, in one line

The target is info.cern.ch, the machine CERN keeps at the address of the first website. It still answers unencrypted HTTP on port 80, which most large sites no longer do, so it is a good place to watch the plain protocol work.

Three details in that command matter. printf rather than echo, because every line of HTTP ends with a carriage return and a line feed and printf writes those two bytes exactly where they are asked for. Connection: close, because HTTP/1.1 otherwise keeps the connection open for a further request and nc would sit there waiting. And two line endings in a row at the end, which is the blank line that ends the headers.

Everything the last chapter described is there and nothing else is. A status line, eight headers, a blank line, then exactly 646 bytes of HTML, the number Content-Length promised. Last-Modified says the file on that disk was written in February 2014 and has not been touched since, which is the clearest possible statement of what a web page is. That is job one done, with no browser anywhere. Sending an HTTP request is not what browsers are for.

All three requests in this chapter are collected in one script if you would rather run them together.

A page is rarely one file

Two things are missing from what nc gave you, and one is worse than it looks. The obvious one is that you have angle brackets rather than a page. The less obvious one is that the CERN page is unusual: it is genuinely self contained. Most are not.

That is the front page of Wikipedia. The twenty four named by src are parts of the page and have to be fetched before it can be shown. The six hundred and fifty two named by <a href> are places you might choose to go, and must not be. The twenty eight <link> tags are the interesting ones, because they are a mixture: some are stylesheets and icons, which are parts, and some are notes for other programs, such as the page's official address and its versions in other languages, which are not. Telling the three apart requires reading the document and knowing what every kind of tag means, and getting it wrong in the generous direction means downloading the encyclopedia to display its front page.

Watching a browser do it

You can watch the whole of job one from the other side, because a server writes down every request it receives. There is a small page in code/07-web-browsers/page/ that names eight other files: a stylesheet, three images, and four links. Serve it and open it in a browser.

Six requests for one page view. The document, then the four files it needs, fetched without being asked because the browser read the document and worked out which references were parts. None of the four links were followed, which is the decision from the last section made automatically. And there is a sixth request nobody wrote down anywhere: browsers ask every site for /favicon.ico whether or not the page mentions one, which is a convention from 1999 that has never been removed. The 404 is the ordinary answer and the browser carries on.

Reload the page and the log tells you something else.

Three hundred and four is a three hundred, so it means look somewhere else, and the somewhere else is your own disk. The browser asked "has this changed since the copy I already have", the server compared the date, and answered with a status line and no body at all. Nothing was transferred. The favicon is the exception, asked for and refused a second time, because there is nothing to remember about a file that does not exist. Your browser's developer tools show this same list under a tab named Network, and it is worth knowing the tab shows you nothing the server does not also know.

The tree the browser built

Job two starts by turning the text into a structure. The tags nest, so the document is a tree, and every browser builds one before drawing anything. It is not hidden: the Elements tab in developer tools is that tree, live, and you can print it yourself from the browser's console. Here is one built from a document written badly on purpose.

Count what was invented. html, head and body appear nowhere in the file. tbody and tr were created to hold a cell that had neither. The two tags closed in the wrong order came out correctly nested. The first paragraph, which is never closed anywhere in the document, was closed by the arrival of the table, so the table is its sibling and not its child. Four repairs, none of them announced, all of them the specification's instructions carried out to the letter.

The job that made browsers enormous

That is the third job, and it is not engineering. In 1991 HTML was about twenty tags and no committee. Mosaic implemented <img> in 1993 without asking anybody; Netscape and Internet Explorer then spent six years competing by inventing tags, and pages started carrying badges saying which browser they required. Standards bodies followed the practice rather than leading it, and a stricter successor that would have refused to display malformed documents was written, ignored, and abandoned, because the web that existed was malformed and always would be.

So the specification gave up on requiring correctness and required identical handling of incorrectness instead. It does not only define what correct HTML means. It defines, step by step, what to do with tags that are never closed, tags closed in the wrong order, and text in places no text is allowed, so that every browser given the same broken document builds precisely the tree you just read. That exists because nobody can edit the pages, and many of their authors are dead.

Check it yourself: leave one header out

Send the same request with the Host line removed, then ask for something that is not there.

terminal
$ printf 'GET / HTTP/1.1\r\nConnection: close\r\n\r\n' | nc info.cern.ch 80
HTTP/1.1 400 Bad Request
Server: Apache
Content-Length: 226
Connection: close
$ printf 'GET /nothing-here HTTP/1.1\r\nHost: info.cern.ch\r\nConnection: close\r\n\r\n' \
    | nc info.cern.ch 80
HTTP/1.1 404 Not Found
Server: Apache
Content-Length: 196
Connection: close

HTTP/1.1 requires that header, and the server refused rather than guessing. Then there is chapter three's decision, arriving as a number, from a real server, in response to a request you typed yourself.

The thing to take from both is what did not happen. You have used a browser thousands of times and it has never once let you send a request without a Host header, or with the line endings wrong, or with the blank line missing. Getting the request exactly right, every time, against servers written across thirty years, is a job you have been handing to someone else without noticing.

Exercises

  1. predict

    Before serving the page above, read index.html and write down how many requests one visit will cost, and which of the eight names it will not ask for. Then serve it, open it, and count the lines in the server's log.

    Six, not five, and the sixth is not named in the document at all. The four <a href> links are untouched, including the one pointing at a page that does not exist, because a link is a place you might go rather than part of what you are looking at. If your prediction was five, you have just learned that a browser asks every site on earth for a file it was never told about.

  2. build

    Do job one for the whole page. Fetch index.html through nc, find every src, every <link> and every <a> in what comes back, sort them into parts and destinations, and then fetch only the parts. Report the number of requests and the total bytes.

    Five requests and about 1,400 bytes, and the four destinations stay untouched. The classification is four lines of pattern matching here and is the part that does not scale: a real page has scripts that name more files while running, images chosen by screen width, and fonts named from inside the stylesheet you have not read yet. Notice also that you fetched them one after another. A browser opens several connections at once, which is why the page appears in less time than the sum of its parts.

  3. break

    Write the tree builder the obvious way: open a tag, go one level deeper; close a tag, come back up; text goes wherever you are. Python's html.parser gives you the events. Run it on broken.html and compare its tree with the one the browser built.

    Four disagreements, and none of them is a bug in your code. Yours invents no html, head or body; it puts the table inside the unclosed paragraph rather than after it; it never creates the tbody and tr the browser conjured; and it ends with the second paragraph nested inside the first. Every one of those is defensible, and every one of them is wrong, because correct here means what the specification says, not what makes sense. That gap is why there are three browser engines in the world and not thirty.

in the wild

Those three engines are Blink, in Chrome and Edge, WebKit in Safari, and Gecko in Firefox. Every application with a web view inside it is running one of them, which is most of the desktop software you use. Electron, the thing behind a great many of those applications, is Blink plus a Node runtime in one package, so the browser you are trying to avoid is running anyway. And the second visit's 304 is the smallest member of the caching family that chapter fifteen takes seriously.

Where this runs out

Everything from chapter four to here has been about the side that asks: how it turns a name into an address, what it sends, what comes back, and what it has to do afterwards.

where this runs out

In every one of those experiments there was a program on the other end that was already running. It had been started long before, it was waiting on port 80, it accepted the connection, read the text, found a file, and wrote text back. We have treated it as scenery. It is not scenery. It is the thing this course is about, and it is smaller than the browser by a very long way. The rest of part four builds it, and by chapter ten you will have written one a browser will talk to.

The first question is the one chapter five raised and measured. A server spends almost all of its life waiting, and the waiting cost 0.4 per cent of a processor for doing nothing at all. So what should it be doing instead? That is chapter eight.
