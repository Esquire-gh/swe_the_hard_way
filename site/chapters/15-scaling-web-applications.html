Part five · more users, more machines

15 · Scaling web applications

What exists at the end of chapter fourteen is a complete piece of software: it answers many people at once, runs your code for each, and remembers what it is told. This chapter is about the different problem that begins when it works and then becomes popular. Each new pressure forces a component into the design, and you have heard all their names, caches and queues and workers and proxies. Here each one arrives attached to the symptom that produced it, and it starts from a number you measure rather than a claim.

Start from a ceiling you measured

Before improving anything, find out what you have. A real page does a few milliseconds of work, reading a database and rendering HTML, so work_server.py does five milliseconds of it per request, in a thread per visitor. Then load.py throws requests at it as fast as a pool of senders can and counts how many complete in three seconds.

Two hundred and thirty five requests a second, and no more, however many senders you add. That is the ceiling, and chapter thirteen already told you where it comes from: the work is arithmetic, the interpreter lock lets one thread do arithmetic at a time, and five milliseconds of it per request is about two hundred requests a second on one core. Everything in this chapter is a way of getting more done without doing more work, and now you can measure whether any of it helped.

Pressure one: the same answer, over and over

Look again at those requests. Almost all of them produce identical bytes, because the guestbook did not change between them. Producing the same answer from scratch every time is the waste, and keeping it so it need not be produced again is caching. The place it is kept is a cache.

Built once instead of a hundred times. You have already met a cache without being told: the response in chapter six carried Age: 14284 and cf-cache-status: HIT, which said that answer had sat in a store for four hours with no machine of the site's involved. The cost arrives in the last lines of that same program.

the puzzle

The data changed and the cached page did not. Nothing crashed, no error was logged, and every visitor from now on is shown a guestbook that is wrong.

When does a cached answer stop being true, and who is responsible for noticing?

A cache is only correct if you have decided in advance when its contents stop being true, and there are two ways to decide: throw it away after a fixed period, which is exactly the time to live from chapter four's DNS, or throw it away when the underlying thing changes, which means knowing every way it can change, including the ones somebody adds next year. Where the cache lives has the same shape as everything else in this course. Inside your process it is fastest and belongs to that process alone, so two processes have two caches that disagree, a fact the exercises make you watch. In a separate program it is shared, and that program is a server in chapter five's sense with its own port; Redis and memcached are that program. In front of everything, near the visitor, it is the cf-cache-status line, and your machines never hear about the request at all.

Pressure two: work nobody should have to wait for

A visitor signs the guestbook, and you would also like to email the subscribers and resize the photo they attached. That is half a second on a good day and thirty on a bad one, and for all of it the visitor watches a blank tab while, as chapter thirteen showed, one of your fixed number of threads is held. The move is to not do the work now. Write down that it needs doing, answer the visitor, and let something else pick it up. The written-down list is a queue, and the program that takes items off it is a worker.

Three costs come with that, and none is optional. The answer changed meaning: it used to say the work is done and now says the work was accepted, so telling the visitor when it truly finishes is a new feature, usually larger than the work itself. The queue in that listing dies with the process, taking its jobs, which is chapter fourteen's problem with chapter fourteen's answer: a real queue is a separate program that writes to a disk. And the worker can die after taking a job, so the queue must keep each job until the worker reports success and give it to somebody else if that never comes. That means a job can run twice.

An operation that can be repeated without changing the result is idempotent. Sending an email is not, which is why real companies have sent you the same notification twice. Making queued work safe to run again, by recording that a given job already ran, is the tax the queue charges for never losing a job.

Pressure three: the process is not immortal

Chapter eleven showed a stranger stopping a server with one malformed line, and correct programs die too: the machine reboots, the process is killed for using too much memory, a disk fills. The site is then down until somebody notices, unless a program whose only job is to watch yours restarts it. That is a process supervisor. The trap is that a program which crashes the instant it starts, restarted forever, looks from a distance exactly like one that is running, so the supervisor must ask whether the program actually works, on an address it answers only when it does. That address is a health check, the first code in this course written for a machine to read rather than a person.

There is a consequence that connects back. Restarting empties the memory, so anything kept in a dictionary is gone, which is why the sessions of chapter eleven belong in a database or a cache and not in a variable, and why signing everybody out on every deploy is a mistake people make only once.

Pressure four: a new version means going down

To install a new version you stop the old process and start the new one, and between those two moments there is no server. Starting the new one first runs straight into chapter twelve: two programs cannot hold one port. So something else holds it, a program that accepts every connection from outside and passes each request to whichever of your processes can serve it, which is chapter twelve's reverse proxy doing its second job. Start the new version on another port, point the proxy at it, let the old one finish what it is handling, and stop it. The whole deploy is one change to where the proxy sends traffic, and it is worth proving that no request is dropped across it.

Fourteen hundred requests through a version change and not one failure. Choosing between several of your processes behind the proxy is load balancing, and this is also where a loose end from chapter four is tied: your application still binds 127.0.0.1 and is unreachable from the internet, and the proxy is the part with the public address, the https certificate, and the exposure to strangers. Making something public is a different program's job, which is why chapters ten and fourteen could ignore it.

Pressure five: it works on my machine

Your laptop has one version of Python and a set of libraries; the deploy target has another and none of them; a colleague's machine has a third combination. Writing the versions down helps and does not finish the job, because those libraries sit on system pieces that also differ. So ship everything underneath the program with it. A container image is your code plus its libraries plus the system pieces they need, as one file that runs the same everywhere, and starting one produces a container. Chapter twelve already showed what that is from the outside: not a second operating system, but ordinary processes scheduled by the same kernel, given a restricted view of the filesystem and network. Docker is the tool most people use to build the images and start the containers. The costs are that images get large, that building them is another step that can fail, and that the isolation is real but thinner than a virtual machine's, which matters when the neighbours are strangers.

Pressure six: you cannot see what is happening

Somebody says the site was slow yesterday afternoon and you have no way to know whether it is true, which part was slow, or whether it still is. The first answer is to write down what happened, one line per request with the path, the status, and the time it took, which is a log, and for a few thousand requests a day it is enough. At a thousand a second nobody reads lines, so the second answer is numbers summarised over time, such as requests per second and how long requests took, which are metrics. One detail there is worth more than the vocabulary: the average lies.

Ten requests in a hundred took half a second, and both the mean and the median hide them: the mean at fifty nine milliseconds looks tolerable, the median at ten looks excellent, and only the ninety fifth percentile shows the tenth of your visitors having a bad time. This is why people quote p95 and p99 rather than the average. The cost is that logs are data at volume: they cost money to keep, they are the easiest place to record a password by accident, and a log nobody reads is a cost with no benefit.

Check it yourself: make the cache lie, then stop it lying

Run cache.py again and look at the last lines, where the page disagreed with the data. The reason is one expression: the key is len(messages), so editing a message without adding one leaves the key unchanged and the stale page is handed back. Change the key to describe the contents rather than count them.

    key = tuple(messages)
terminal
the messages now start: 'Ada was here, and edited it'
the cached page says:   '<li>Ada was here, and edited it</l'
pages built in total:   2

The staleness is gone, and the last line is what it cost. The first version built one page for everything; this one built two, because an edit now produces a key it has never seen. A hundred edits would build a hundred pages. That is the whole subject in one expression: a key that can never be stale is a key that misses more often, and every real caching decision sits between those two runs.

Exercises

  1. predict

    You run two copies of your server behind the proxy, each with an in-memory cache, and each caches the current time on its first request. A visitor's first request lands on one copy and their second on the other. Predict what they see, then run two_caches.py.

    Two different times, because a cache inside a process belongs to that process alone, and the two copies filled their caches a second apart. This is the flaw in the fastest kind of cache: the moment you have more than one process, which is the moment you deployed with the proxy, an in-process cache is per-process, and visitors see whichever one the load balancer sent them to. The fix is the shared cache from the chapter, a separate program both processes talk to, which is slower per request and consistent across all of them.

  2. build

    Combine the deploy and the supervisor. Run two copies of a backend behind the proxy, have the proxy spread requests across the healthy ones, and kill one with kill -9 mid-stream. Make the proxy notice and stop sending to the dead one, so no visitor sees a failure, then bring it back.

    balance.py does it and reports zero failures through the kill. Two pieces make that work: a health check that marks a backend down, and a retry that, when a connection fails anyway, sends that one request to another backend instead of returning an error. The health check alone is not enough, because the request in flight at the instant of the kill was sent before the check noticed. This is load balancing, health checking, and failover, and you built all three in under eighty lines. The managed versions differ mainly in that somebody else runs them.

  3. break

    Break a cache the dangerous way. Cache a page that is different for each visitor, the logged-in home page, under a key that is only the path. Then load it as one person and again as another, and see what the second person is served.

    The second visitor is handed the first one's private page, greeting them by the wrong name and, in a real application, showing them somebody else's messages. wrong_key.py shows it in a few lines. This is not a performance bug, it is a data leak, and it is among the most common serious cache mistakes there is. The rule it teaches is exact: the cache key must include everything the answer depends on, and a per-user page depends on the user. The stale-page bug in the check made a page wrong; this one makes it wrong on purpose, for the person who should never have seen it.

in the wild

Every component here has an industrial name. Cache-Control and ETag are the time-to-live and the content key from this chapter, sent as headers so the browser keeps the cache for you. Celery and Amazon's SQS are the queue and worker as a service. systemd is the supervisor on most Linux machines, with health checks written into a unit file. nginx's upstream block is the proxy and its list of backends. Prometheus is the metrics store the percentiles come out of. And Kubernetes is the sentence "the platform does it" made real: it runs the supervisor, the health checks, the load balancing, and the zero downtime deploy you just wrote, across many machines, from a description of what you want rather than a program that does it.

Count what you wrote by hand

Read back over the six fixes and notice what they share. The cache, the worker, the supervisor, the proxy, the container: every answer in this chapter is an arrangement of processes, as described in chapter one, on one computer. Chapter seventeen is about the day that stops being enough.

where this runs out

Before that, count. Since chapter ten you have written, by hand: an accept loop, a request reader that counts bytes, a router of if statements, a query string parser, a form parser, a header parser, a cookie parser, a response builder, a redirect builder, an escaper, a thread per visitor, a lock, a database schema, a cache with a key, a queue with a worker, a health check, and a load balancer. Every one was tedious, every one is easy to get subtly wrong, and every one is identical in every web application anyone has written.

That combination is exactly what a library is for, and a library large enough that your code sits inside it has a name. Chapter sixteen is the first thing this course installs.
