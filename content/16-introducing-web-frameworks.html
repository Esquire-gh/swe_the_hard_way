Part five · more users, more machines

16 · Introducing web frameworks

Every tutorial you have followed started here, with an install command, and this course has waited fifteen chapters to run one. That was deliberate. Chapter fifteen ended by counting what you have written by hand since chapter ten, and every item on that list was tedious, easy to get subtly wrong, and identical in every web application anybody has ever written. Now there is a list of specific problems to buy solutions for, and the rule for this chapter is strict. Nothing appears here that cannot be pointed at a block of code you already wrote.

Why everybody uses one

Chapter eleven ended with a hundred and three lines that are a guestbook, in the sense that a car is a journey. About thirty of them are about signing a book. The rest is machinery, the machinery is unfinished, and the unfinished parts are the ones that let a stranger take the server down with one line.

That combination, tedious and risky and the same everywhere, is exactly what a library is for, and a framework is a library large enough that your code sits inside it rather than the other way round. You do not call a framework. It calls you. That sentence is the whole difference, and the rest of this chapter is watching it happen.

Line by line against what it replaces

Now the point of the chapter. Every piece of that file is standing where something you wrote used to be.

The accept loop is gone. The bottom of every step file in chapter eleven was the same eight lines: make a socket, set SO_REUSEADDR, bind, listen, print, loop forever, accept, close. That is now the word uvicorn in a command. You do not run app.py because app.py is not a program. It is a collection of functions that uvicorn calls, which is what it means to say your code sits inside the framework.

read_request is gone. Chapter eleven counted bytes against Content-Length in a loop, and admitted that the loop would happily try to collect four billion bytes if a stranger asked it to. Uvicorn reads the request, and it also enforces the limits and timeouts that chapter eleven listed as missing.

The chain of if statements is gone. handle decided what to do by comparing the path against a series of strings, in a function far away from the code that answers. Now @app.get("/") sits directly above the function that answers GET /. The routing moved to the thing being routed to.

The 405 branches are gone. Chapter eleven needed explicit code so that a POST to a page that only reads returned 405 rather than 404. Here, registering / for GET is enough. Anything else arriving at / gets a 405 that nobody wrote.

split_target and parse_fields are gone. Chapter eleven pulled fields apart on & and = and undid the percent encoding, once for the query string and again for the body. Here it is name: str = Form() in the function signature. The field is named where it is used, and if it is absent the framework answers rather than the function crashing on a missing key.

headers_of and cookies_of are gone. Two more parsers, each with its own separator, replaced by session: str = Cookie(default="").

The redirect builder is gone. RedirectResponse("/", status_code=303) does what those four lines of string joining did, and the post then redirect then get reasoning from chapter eleven is unchanged. The framework did not remove the need to understand that, and it should not.

The response builder is gone. Chapter eleven assembled a status line, Content-Type, Content-Length and Connection for every reply. Returning a value now does it.

escape is gone, and this is the important one. Chapter eleven's fix was a function you had to remember to call at every single place text from outside entered a page, and the chapter said plainly that the one you forget is the bug. Look at app.py and the templates and find the call. There is not one. Jinja2 escapes everything placed into a page unless it is explicitly told not to, which is why <b>first</b> came back as &lt;b&gt;first&lt;/b&gt; above. The rule moved out of your memory and into the tool. That is the difference between a habit and a property.

String pasting is gone. Chapter eleven's guestbook_page built HTML with an f-string wrapped around a generator expression. The template has a loop, an empty case, and readable HTML, and a person who writes pages rather than Python can edit it.

The list is gone, and this one is chapter fourteen's doing rather than the framework's. Messages go into a table, through a ? slot rather than a pasted string, and connect opens a fresh connection for each request. The comment on it says why, and the reason is chapter thirteen. Several of these functions are running at the same moment, on different threads, and a connection is not something two of them may share.

The page chapter eleven could not write

Chapter eleven finished by asking you to imagine a page showing one message by number, at /messages/3, and pointed out that a chain of equality checks cannot express it. Here it is, and it is the last function in the file. The {number} in the path is the pattern matching chapter eleven said would have to be written from scratch. The number: int is the part worth stopping on. It is an ordinary Python type annotation, and the framework reads it and enforces it before your function runs.

Three different wrong things, three different answers. The 404 is yours, since only your code knows which messages exist. The 422 for banana is the framework's, and your function never ran, because a value that cannot be an integer never reached it.

What the framework quietly handles

Some of what it took over is visible in the listing as an absence. Some of it is not in the listing at all, and those are the pieces you cannot afford to accept without recognising them.

The first is chapter thirteen. Two people can use this guestbook at once, and nothing in app.py says a word about how. Uvicorn runs an event loop, the one chapter thirteen named, and hands each of your ordinary def functions to a thread from a pool so that a slow one does not stop the loop. Your functions run on a thread, the functions around them run on other threads, and the lock chapter thirteen made you write is not in the file at all. The reason it can be left out is not that the framework removed the race. It is that the shared state moved into a program that already knows about concurrent writers, which was chapter fourteen's argument for a database in the first place. The one piece of state still held in a dictionary, sessions, is exactly as unprotected as it was in chapter eleven.

The second is chapter eleven's crash. Send the hand written server a line that is not a request and it prints a traceback and exits. Send the same line here.

A 400, and still serving. The line that killed chapter eleven's server was the one that split a request line into three parts and assumed there were three. Uvicorn makes no such assumption, and the whole of the reading code is somebody else's problem to keep correct.

Two smaller things arrived unasked. The cookie came back with SameSite=lax on it, which stops a different site from making a visitor's browser send requests to yours, and nothing in app.py requested it. And because the routes are now declarations rather than if statements, they can be read by other code, so the framework can describe its own interface.

There is a browsable page of documentation for a program you did not document. That is not magic. It is the direct consequence of having written the routing down as data instead of burying it in control flow.

The same thing under other names

FastAPI is one of many, and now that you can see what it is made of, the others are easy to place. Flask and Django in Python, Express in JavaScript, Rails in Ruby, Spring in Java, Laravel in PHP. Every one of them is the list above: a loop somebody else runs, a router, parsers for fields and cookies, a response builder, and a template engine that escapes by default. What they differ in is how much else they bundle. Flask and Express ship the list and little more, and you choose the database layer and the session store yourself. Django and Rails ship the list plus a database layer, a session store, an admin interface and a way to log in, and the word for that is batteries included. Neither is better. One is a smaller thing to understand and the other is a smaller thing to assemble.

The vocabulary on their front pages is the same vocabulary too. Routing is chapter eleven's if chain. Middleware is code that runs on every request before yours, which is where chapter fifteen's logging and chapter eleven's cookie reading go. An ORM is a library that turns chapter fourteen's SQL into method calls on objects, and it is still SQL underneath. Sessions are chapter eleven's dictionary, moved to a database or a cache for chapter fifteen's reasons. If a framework's documentation names something you cannot place in this course, that is the thing to look up first, because it is either a new idea or, far more often, an old one with a new name.

What a framework does not do

This should feel like relief rather than cleverness. Every line of it is doing something you did by hand and can still describe. It is also worth being exact about what did not move, because the tutorials that start with the install command tend to leave the impression that everything did.

The framework does not know your data. The table, its columns, the NOT NULL, and the decision to index a column or not are chapter fourteen's and remain yours. It does not stop you pasting a string into a query, since the ? slot is something you choose to use, and an ORM makes the safe way the easy way without making the unsafe way impossible. It does not pick your cache keys, and chapter fifteen showed what a wrong one does silently. It does not make anything idempotent. And it does not know what your site is for, which is why the thirty lines that remain are the thirty that were always the point.

One machine has a ceiling

That is the install command, fifteen chapters late and, for the first time in your experience of one, completely explained. Everything behind it is something you have written a small version of.

where this runs out

Look again at what the framework is running on. One process, on one machine, with a thread pool whose size is a number in a configuration file. Chapter fifteen's answers, the cache and the queue and the worker and the proxy, were all processes on that same machine. The framework does nothing about that, and cannot, because the machine is the thing with the ceiling. At some number of visitors the processor is busy all the time, or the memory is full, or one disk cannot be read fast enough, and no arrangement of processes on that computer helps.

The next move is a second computer, and then a tenth, and the moment a system spans more than one machine a specific list of things that were reliably true stops being true. That list is chapter seventeen.
