Part four · building the server

10 · Building a static web server

Every piece is now on the table: the loop that waits, the calls that fill it, and the text that goes in and out. What is left is to put them together, and the answer is about twenty lines. Most of this chapter is about the next twenty, which turn it into the oldest kind of web server there is: one that keeps a folder of files and hands them out. The path in the request names a file in the folder. If the file is there, send it. If it is not, say so. That mapping is the whole of what a static web server does, and getting it slightly wrong is the first security bug you will write.

The path names a file

Chapter four said a website is a file on somebody else's computer, and this is the chapter where that becomes literally true, so it is worth saying exactly what the program is going to do before writing it. The server keeps one folder, and that folder is the website. Here it is called site/, and the general name for it is the document root. When a request arrives, the server takes the path from the request line, joins it onto the end of that folder, and looks for a file there. /about.html means the file site/about.html. A path that names a folder rather than a file, like /, means the file called index.html inside it, a convention that dates from the first web server and that every one since has kept. If the file exists, its bytes are the body of the response, and its extension decides the Content-Type label. If it does not exist, the response is a 404, which is chapter three's decision that links may break, arriving as a number from your own code.

A server that does this and nothing else is a static web server, and a site made entirely of files that are handed out unchanged is a static site. Static means that every visitor who asks for a path gets the same bytes, because the bytes are sitting on a disk and nobody is computing anything. The page you are reading now is served this way. Most of the web was, for its first few years, and the moment a page has to differ from one visitor to the next is where chapter eleven begins.

The same calls, with Python's names on them

Python's socket module is a thin covering over the calls from chapter nine, and most of the names line up exactly. socket.socket() is socket, and then bind, listen and accept are called bind, listen and accept. Two names differ, and both differences are worth knowing. Reading is recv rather than read, and it takes a maximum number of bytes. What comes back is whatever has arrived so far, up to that maximum, which is the point from chapter six about a stream having no message boundaries, showing up in an argument list. Writing is sendall rather than write. The plain send may write only part of what you gave it and return how much it managed, while sendall loops until everything has gone. Using send and ignoring the number it returns is a real way to lose the end of a page.

One line in the listings below has no equivalent in chapter nine and needs a word now.

server_socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)

When a server stops, the operating system keeps its port reserved for a minute or two, in case packets from the finished conversations are still in flight. Without that line, restarting your server during that window fails with address already in use, which you would otherwise meet about four minutes from now and find baffling.

Serving the folder

Now the mapping from the start of the chapter, which is the change that makes this a web server rather than a demonstration of sockets. answer takes the path and does exactly what was described: it joins the path onto ROOT, swaps a folder for its index.html, sends a 404 if nothing is there, and otherwise reads the bytes and picks a label from the extension. There is a small site to serve, holding two pages and a stylesheet. The file below contains a bug on purpose, and the section after it is about the bug.

Point a browser at it and the site works. Following the link to the second page works, the stylesheet arrives and the page is laid out, and the server's own window shows why.

Three separate requests, three separate connections, three separate trips through accept. The browser asked for the page, read it, found that it referred to a stylesheet, and came back for that, which is the second job from chapter seven being done for you. Your twenty lines did not have to know anything about stylesheets to serve one, because Content-Type is a label and the browser does the rest. The third line is a request for a file that does not exist, and the server answered 404, exactly as the mapping says it should.

The bug you just wrote

Now the part that makes this a chapter about writing servers rather than a chapter about sockets. ROOT / path.lstrip("/") joins whatever the visitor typed onto the end of your directory. Visitors are strangers, and one of the things a stranger can type is .., which means the folder above.

the puzzle

Next to your server, outside site/, there is a file called not-for-the-public.txt. Nobody visiting the site should ever be able to read it. A browser will not ask for it, because browsers tidy up paths before sending them. But chapter seven showed that you do not need a browser, and nc will send exactly the bytes you type.

What does your server hand back for GET /../not-for-the-public.txt?

Enough ../ and the same request reads any file the server process has permission to open, anywhere on the machine. This has a name, path traversal, and it is one of the oldest mistakes in web software. It is worth seeing on your own server, in a file you wrote, because the line that causes it looks completely reasonable. The fix is to work out the real location the path resolves to, and refuse anything that is not inside the directory you meant to serve.

resolve follows the .. parts and any shortcuts on the disk and reports where the path genuinely lands. Then the check is whether the directory you are serving is one of its parents. The same request against the corrected server gets nothing but a refusal.

Keep the shape of that reasoning, because it recurs for the rest of this course. Everything arriving from outside is text a stranger chose, and every place your code uses it to reach something is a place where the stranger is choosing what you reach.

The request that has not finished arriving

There is a second bug in that file, and it is not a security hole, it is the chapter six problem arriving in your own code. The server calls recv once and treats whatever comes back as the whole request. Chapter six said a stream has no message boundaries. Nothing promises that the bytes a browser sent in one piece arrive in one piece, and the way to find out what your server does about it is to send a request in two pieces on purpose.

Nothing here is malformed. The bytes are right and they arrive in order. They are only late.

The visitor asked for /about.html and got the front page, with a 200 on it saying everything went well. The server's own window agrees with itself.

It read GET /ab, split it on spaces, found /ab where the path goes, could not find that file, and, because /ab is not a real path, fell through to the front page. No error was raised, nothing was logged as wrong, and the visitor has a page that is not the one they asked for. This is the failure mode worth recognising: not a crash, but a wrong answer delivered confidently. Fixing it means reading until the blank line that ends the headers has arrived, which is what a real server does and what chapter eleven has to do, because that is where request bodies start showing up and bodies are where the bytes get long enough for this to happen by accident.

The one you already had

Python ships a static web server, and it is worth meeting now rather than earlier, because you can now read it.

Same folder, same site, same two hundred and same four hundred and four. It is the program you wrote, with the parts you left out filled in. Two of those parts are worth naming. The first is the table that turns a suffix into a Content-Type: yours has four entries, and the one Python ships with has 1,033. The second is the guard, which lives in a method called translate_path and can be read in a few lines.

Decode first, then tidy the path, then walk it a piece at a time and drop any piece that is . or ... Notice the order, because the first exercise is about exactly that order. Notice also that it differs from yours in what it does when it catches something: yours refuses with a 403, and this one quietly removes the offending part and carries on, which is why both of the escape attempts above came back 404 rather than 403. Neither is wrong. They are two answers to the question of what to tell a stranger who is trying doors.

That is worth a moment, because it is the definition of the thing being served. There is no website inside your program. There is a directory, and a program that will read out of it when asked.

Exercises

  1. predict

    A stranger asks for /%2e%2e%2fnot-for-the-public.txt. Those escapes are how a URL writes ../, and chapter four's rules say a server must decode them. Now imagine three guards. One refuses any path containing .., then decodes. One decodes, then refuses any path containing ... One works out where the path lands and refuses anything outside the folder. Which of the three let the file out? Write your answer down before running encoded.py.

    Only the first one leaks, and it leaks because it looked for the dangerous text before the text turned dangerous. At the moment it checked, the path said %2e%2e%2f, which contains no .. at all. The order of two lines is the whole bug. The second guard survives these four requests, but it is still reasoning about what the path says, and you would have to think about every way .. can be written to trust it. The third does not care what the path says, only where it ends up, which is why it is the one you want and the one http.server approximates.

  2. build

    Your Content-Type comes from the end of the filename, which trusts whoever named the file. Most formats begin with a few fixed bytes that say what they are. Build a second table that reads the first sixteen bytes instead, run both over a folder, and make sure that folder contains a file whose name is lying.

    Two rows disagree, for opposite reasons. trust-me.html is a PNG with an HTML name: the suffix says text/html, the bytes say image/png, and a browser told text/html will try to render a binary file as a page. But look.css is a real stylesheet the bytes cannot identify, because CSS has no fixed opening, so sniffing demotes it to text/plain and the page loses its styling. Neither method wins. This is why the real answer is a server that reads the suffix, a X-Content-Type-Options: nosniff header that tells the browser to stop guessing, and a rule that visitors do not get to upload files into your document root.

  3. break

    The fix asks where a path lands. Make a shortcut inside site/ that points at the private file next to it, so that every character of the path is innocent and the path never leaves the folder. Predict what the guard does before you run it.

    It refuses, with the same 403, because resolve follows shortcuts on the disk and reports the destination rather than the route. That is the guard doing more than you asked. Notice what it costs: a legitimate shortcut inside your site, pointing at a shared folder of images, would be refused too. nginx has a setting for precisely this argument, disable_symlinks, and it is off by default, meaning nginx follows them. Every one of these guards trades a real thing away to close a door, and the job is knowing which trade you made.

in the wild

nginx configuration is answer() written as settings. root /var/www; is your ROOT, index index.html; is the folder rule, and try_files $uri $uri/ =404; is the three lines that look for the file, then the folder, then give up. When a CDN serves a page from a machine near you, the program on that machine is this one with a very large folder and rules about how long a file may be kept before being fetched again. The whole first decade of the web ran on this chapter, and the page you are reading is served this way now.

Where this runs out

You have a web server. It hands every visitor the same bytes, which is what static means, and it deals with one visitor at a time, forgetting everything when you stop it. Those are limits real servers had, and the order in which they were fixed is roughly the order of the rest of this course.

where this runs out

The mapping this chapter is built on, one path to one file, cannot greet somebody by name, show one person their own messages, or accept a single character a visitor types. There is no file on the disk with your name in it, and there cannot be one for every visitor.

The moment a page needs to be different for each visitor, reading a file stops being enough. Something has to run, per request, and produce the answer. That one change is chapter eleven.
