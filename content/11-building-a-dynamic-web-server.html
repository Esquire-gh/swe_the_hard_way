Part four · building the server

11 · Building a dynamic web server

Every site you actually use knows who you are. It greets you, shows you your messages and not somebody else's, and takes what you type. The server from chapter ten can do none of that, because it reads a file and the file does not change. Making a page different for every visitor is one line in the server: call a function instead of reading a file. This chapter is everything that happens after that one line, written out in full, because it is the part a framework makes disappear and the part this course exists to show you.

One line, and then a pile

A page that is read off a disk and sent unchanged is a static page, and for the first few years that was the whole web. A page that is produced by running code at the moment of asking is a dynamic page, and every site that greets you by name is made of them. The difference in the server is exactly one line. Instead of reading a file and sending it, call a function and send whatever it returns. The program that runs the function is doing a different job from the one in chapter ten, and chapter twelve gives that job its name. Nothing in what follows is hard. There is a great deal of it, and the pile is the point.

Step one: deciding which code answers

With files, the request path was a filename. With code, the path has to select a piece of code, which means writing down the correspondence yourself. Choosing which code answers which path is called routing.

Note what had to be decided rather than discovered. The method has to be checked, because chapter six gave the client several, and a POST to a page that only reads is a different failure from a page that does not exist. A path that matches nothing needs a 404, a path that exists but rejects the method needs a 405, and if you do not write both then one of them silently becomes the other. This is a chain of if statements, it is thirty five lines, and it is fine. Hold on to the feeling that it is fine.

Step two: reading what the visitor typed into the address

The address bar can carry more than a path. Everything after a question mark is a list of fields, written as name=value joined by &, and it is the oldest way for a visitor to send something. That part of the address is the query string.

unquote_plus comes from the standard library and turns %20 and + back into spaces, because the field encoding cannot contain a space, an ampersand or an equals sign without disguising it first. Even here, in the middle of doing everything by hand, a library is doing a job you would otherwise have to write. Now a page can use the fields.

Then somebody who is not you asks for a page.

The visitor supplied part of the page rather than part of the text. A browser receiving that runs the script, because there is nothing in the bytes to suggest it was not meant to be there. Send somebody a link with that in it and the script runs in their browser, on your site, with whatever access their session has. The name for this is cross site scripting, and it is the path traversal from chapter ten wearing different clothes. Text arrived from a stranger and was used as though you had written it. The fix is to turn the characters that mean something in HTML into the codes that mean the characters.

Read that fix again and notice its shape, because the shape is the problem. escape has to be called at every single place where anything from outside is put into a page. Not most places. Every place. The one you forget is the bug, it will not show up in testing because you will type your own name into the form, and the file is now fifty two lines.

curl printed that script back and nothing happened, which is misleading, because curl does not run scripts. A browser does. cookie_theft.py, in the exercises folder, serves the unescaped page and hands the visitor two cookies, so you can point a real browser at the same crafted address and watch the injected script execute on your own page. What it can and cannot read once it runs is the subject of step four, and it is a sharper lesson seen than described.

Step three: accepting something and keeping it

A guestbook needs a form, and a form needs a method other than GET, because GET puts the fields in the address where they get bookmarked, logged and shared. Three separate pieces of work arrive at once here, and each one looks small.

The first is reading the body at all. Chapter six made the point that a stream has no message boundaries and that the length is stated in a header. Chapter ten ignored that and took one bufferful. Once there are bodies, ignoring it stops being survivable.

The second is that a form body is encoded exactly like a query string, so the field parser from step two is needed again, in a second place, for a different reason. The third is what to do after the visitor has posted something. The obvious answer is to return the updated page. The correct answer is to send a redirect.

The reason is that a browser remembers the request that produced the page it is showing. If a POST produced it, then reloading repeats the POST and signs the guestbook again, and so does the back button. Answering with a 303 makes the browser fetch the page with a fresh GET, and that is the request it remembers. This pattern is called post redirect get, and every person who has not done it has shipped a form that duplicates entries.

The escaping is being remembered, this time. Seventy three lines.

Step four: knowing who is on the other end

Now the part that most people find genuinely surprising the first time. The protocol from chapter six has no notion of a visitor. Every request is complete on its own, arrives on its own connection, and carries no relationship to any request before it. The server has no memory of you between one request and the next, and cannot have, because there is nowhere for that memory to live in the message. This property has a name, and HTTP is described as stateless.

So being logged in has to be built out of nothing. The method the web settled on is to have the server hand the visitor a piece of text and have the browser send it back on every subsequent request. That piece of text is a cookie.

Reading it back requires pulling apart a header with its own separate format, which is a third parser in the same file.

The cookie holds a random number and nothing else. The name lives in a dictionary on the server, and the cookie is only the key to it. That arrangement is a session, and doing it the other way, putting the name in the cookie, means any visitor can edit the cookie and become anybody. secrets.token_hex is used rather than anything simpler because the token is the only thing standing between a stranger and somebody else's account. A guessable session id is an account anybody can take. HttpOnly tells the browser not to let scripts on the page read the cookie, which limits the damage from the mistake in step two. Two more words belong on that line in real code. Secure tells the browser to send the cookie only over an encrypted connection, so it cannot be read off the wire. SameSite tells the browser not to send it when the request came from another site, which is a different attack from step two and one this course does not otherwise reach. None of the three is the session; they are instructions to the browser about when it may show the key back.

Two visitors, one server, two different pages. That is the thing chapter ten could not do, and it took a hundred and three lines to get here.

Check it yourself: read the file you now have

Open step4_session.py and read it from the top, without skipping. Count how much of it is about a guestbook. There is a list of messages, a dictionary of sessions, two functions that produce pages, and about fifteen lines inside handle that decide what to do. Call that a third of the file, being generous.

Everything else is machinery, and none of it is specific to this program: the response builder, the redirect builder, the escaper, the field parser, the header parser, the cookie parser, the request reader that counts bytes against Content-Length, the socket setup, the accept loop, and the close.

Now imagine the next page. Not a hard one. A page that shows one message by number, at /messages/3. The chain of if statements cannot express it, because the number is part of the path, so the routing has to grow a way to match patterns and pull pieces out. That is a new subsystem, and it will be written badly the first time. Then imagine the twentieth page.

The things that are still wrong

The file works, and a fair description of it is a hundred lines of machinery holding thirty lines of guestbook. That would be tolerable if the machinery were finished. It is not, and the worst gap takes one line to demonstrate. Send the server something that is not a request.

The server is gone. Five words that are not a request line, and the process that was serving everybody has exited, taking the guestbook and every session with it. Chapter five said a server that stops working because somebody sent it something unexpected is a server any stranger can turn off, and this is that server. The right answer was a 400, which chapter six listed and this code never sends. The exercises below make you provoke two more failures the same way, by hand, because the point of this chapter is that you can now see them coming.

The rest of the list is shorter to state than to fix. Escaping is a rule in your head rather than anything the design enforces, so the one page you forget is the hole. Every page builds HTML by pasting strings together, which stops being readable the moment a page has a loop and a condition in it. There is no logging, so a request that goes wrong leaves no trace of what was asked. And everything the process is holding, the messages and the sessions alike, disappears the moment you press control C, because it lives in memory belonging to a process.

None of that has anything to do with the guestbook. It is not that any of it was difficult; it was tedious, it is easy to get subtly wrong, and it is identical in every web application anybody has ever written. Chapter sixteen is where that observation turns into something you can install.

Exercises

  1. predict

    A form has one field called name, and a visitor sends it twice: name=Ada&name=Grace. Read parse_fields and say which value the page ends up with, and why. Then predict what Python's own parse_qs does with the same bytes.

    Our parser keeps Grace, because each pair overwrites the last into the same dictionary key, so the last value wins. parse_qs keeps both, returning {'name': ['Ada', 'Grace']}, because it was built by people who had been bitten. The gap matters: a login form that trusts the first value while a filter trusts the last is a real class of bug, and it exists because the format allows a repeat and never says what a repeat means. You had to decide, and you decided by accident.

  2. build

    Add a page at /messages/3 that shows one message by its number. The chain of if statements cannot express it, because the number is part of the path, so write the matching by hand: split the path, check the first piece is messages, turn the second into an integer, and answer 404 when it is not a number or not in range.

    You have just written the beginning of a router. Notice how much care the integer takes: a missing number, a number that is not a number, and a number with no message behind it are three different 404s, and you wrote all three. Now imagine /users/12/messages/3, and imagine twenty such patterns. What you are feeling is the exact pressure that produced @app.get("/messages/{id}"), and chapter sixteen is where that line arrives already written.

  3. break

    Two failures, both one client program. First claim a Content-Length of four billion and dribble a body in, and watch read_request collect it until memory runs out. Then open a connection, send half a header, and go quiet, and watch the whole server stop. Fix the second one with a single line.

    oversized_body.py holds five hundred megabytes of one request before its own safety valve stops it, and the real loop has no valve. slow_header.py shows the server stuck inside recv, unable to accept anyone else, because chapter eight's blocking is doing exactly what it was told. The fix is connection.settimeout, which turns the endless wait into a socket.timeout you can catch and answer with a 408. Both attacks cost the attacker almost nothing and cost you the whole server, which is why a real server caps the body size and times out a slow client before it does anything else.

in the wild

Every function in this file has a name in a framework. Flask's session is the dictionary you built in step four, except the token is signed rather than stored, so the server keeps nothing. A Jinja template is guestbook_page with the string pasting replaced by a page that escapes by default, so the mistake in step two becomes the thing you have to ask for rather than the thing you forget. @app.route is the if chain in step one, written once and read by the framework. None of it is new work. It is this chapter, packaged so you write the thirty lines and not the hundred.

Two programs, one word

You now have two programs. One reads files off a disk and sends them back, and one runs your code to produce the answer, and they are doing different jobs.

where this runs out

Both of them are called a server. So is the laptop they are running on, and so is the machine in a rack that will eventually run them for real. One word is carrying at least three meanings, and most writing about this subject uses it without saying which, which makes that writing harder to read than it needs to be.

Sorting the word out takes five minutes and one small program, and it is chapter twelve.
