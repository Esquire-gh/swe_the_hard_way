Part three · the conversation

05 · Clients and servers

You have heard client and server, or front end and back end, often enough that they sound settled. What makes one program the client and the other the server is a single fact, so obvious it is almost never said out loud: one of them was already running, and the other one started the conversation. Everything else people believe about the two words follows from that, or is wrong.

One of them was already there

The last chapter got us as far as a machine and a path. There is a computer with a file on its disk, we can turn a name into its address, and chapter two gives us an ordered stream of bytes between two programs once they are joined up. What has not been settled is anything about the two programs. One has the file and one wants it, and every other detail is open.

Start with the machine that has the file. It cannot spring into life when you ask for something, because nothing on it would hear you. For your request to be heard, a program on that machine must have been started already, and must have been sitting there doing nothing, waiting for somebody to arrive.

That gives the two roles. The program that starts the conversation, because it wants something, is the client. What it sends is a request. The program that was already running is the server, and what it sends back is a response. This arrangement, one side waiting and the other side asking, is what the field calls the client server model. When you see client side and server side, or front end and back end, this is the line being drawn.

Three consequences are worth having in mind before you meet them as bugs. A server does not know its clients in advance: it has no list of who might call, finds out you exist when you arrive, and usually forgets you when you leave. The conversation can only be opened from one end, so a server cannot ring you up, which is why for years a page that wanted to show you a new message had to keep asking whether anything had happened yet. And clients arrive whenever they like, in unpredictable numbers. A server with one visitor and a server with a thousand are the same program in a different situation, and coping with that difference is most of part five.

It is a role, not a kind of machine

This is worth stressing, because the word server also names a kind of computer, and that makes people picture the role as something only a machine in a data centre can play. It is not. The role belongs to the conversation. The same computer can be a client in one conversation and a server in another at the same instant. Your laptop is a client while you read a page, and a server if you are sharing your screen, running a development server, or letting a phone in the house print through it. None of that changes what the machine is. The only thing that decides the role is who initiated the request and who returned the response.

The arrangement is also a convention rather than a law. Nothing in chapter two is asymmetric: any address may send a packet to any other, and the routers in the middle do not care which end started it. Systems where every program does both jobs at once are real, and file sharing networks are the well known example; the arrangement is called peer to peer. Client and server won partly because it is easier to reason about, and partly because most machines now sit behind a shared public address and cannot be reached from outside at all.

Watching the two roles run

We do not yet know how a program listens for somebody arriving over a network, because that is chapters eight and nine. So here the two programs talk through a directory on the disk. The channel is a placeholder; the roles are the subject.

The waiting half checks a mailbox directory for requests, answers each one into a matching file, and goes back to checking.

The starting half writes one request, waits for its answer, and exits.

Start the waiting one in a terminal and leave it alone, then in a second terminal ask it three things.

While that happened, the first terminal filled in.

The process ids are the part to read closely. Three separate client processes ran, 88021, 88050 and 88051, each of which existed for a fraction of a second and then died. Every one was answered by process 88019, which was there before any of them started and is still there now. That is the asymmetry, in numbers.

The third answer matters too. The client asked something the server had never been taught, and the server answered anyway, saying what was wrong. It did not crash and it did not go quiet. A server that stops working because somebody sent it something unexpected is a server any stranger can turn off, and strangers are the entire audience. Now replace the directory with a network connection and you have a web server. That substitution is chapters eight through ten, and nothing in the shape above changes.

What waiting actually costs

There is a lie of omission in the paragraph that said the server sits there doing nothing. Look at the last two lines of waiter.py. It is not doing nothing. It is looking in the directory, finding nothing, sleeping for fifty milliseconds, and looking again, twenty times a second, forever. That has a price, and it is measurable.

Two processes, both of them idle by any reasonable description, and only one of them costs anything. The sleeping process is genuinely asleep: the operating system will not consider running it until forty seconds have passed, so it uses no processor at all. The server is awake twenty times a second to ask a question whose answer is almost always no.

The exercises measure the other side of the same coin. A client asks and gets its answer in about forty milliseconds, and almost all of that is spent waiting for the server's next look. Poll less often and the machine does less work while every answer gets slower. Poll more often and the reverse. There is no setting that is good, which is a strong hint that the whole approach is wrong and that something else must exist.

carry this forward

What you want is a way for a program to say "wake me when somebody arrives, and until then do not schedule me at all", and get the zero in the second row without the fifty millisecond delay. That is what real servers do, the operating system provides it, and chapter eight is about how.

Check it yourself: ask when nobody is listening

Stop waiter.py with control C, then run the client on its own.

terminal two
$ python3 asker.py time
process 60336 asked 'time' and is now waiting
nobody answered. is waiter.py running?

Nothing the client can do will produce an answer. It cannot start the server, because starting a program on somebody else's machine is not something a network lets you do, and that is deliberate. The server has to already exist, which is the claim this chapter opened with, and it fails in exactly the way a browser fails when a site is down.

Then look at how many programs on your own machine are currently playing the server role.

terminal
$ lsof -nP -iTCP -sTCP:LISTEN
COMMAND     NAME
rapportd    *:50108 (LISTEN)
ControlCe   *:7000 (LISTEN)
ControlCe   *:5000 (LISTEN)
...and more, from applications you installed and forgot about

The names have been trimmed here, because the full list names everything the author has installed. The word LISTEN is the operating system's record of a program that has asked to be told when somebody arrives, which is the mechanism chapter nine is about. The point of looking is the count. You did not start most of these and you would not describe any of them as a server, and yet each is the waiting half of some conversation. Your laptop is a client and a server at the same time, right now.

Exercises

  1. predict

    Start waiter.py twice, in two terminals, on the same mailbox, then ask six questions from a third. Before you run it, write down which of the two process ids answers each question, and how you know.

    One of them answers all six and the other answers none, and which one is arbitrary. There is no rule anywhere deciding it: both wake up twenty times a second, and whichever happens to look first takes the file and deletes it before the other one's turn comes round. Nothing in the design shares work, balances it, or even notices that a second copy exists.

  2. build

    Teach the waiter two questions it cannot answer today: count, how many questions it has answered since it started, and uptime, how long it has been running. Then write a client that gives up after half a second instead of five, and print how long each answer actually took.

    Answers arrive in about forty milliseconds, and count climbs across separate client processes that never met each other. That is the asymmetry doing real work: the client is too short lived to remember anything, so anything worth remembering has to live on the side that was already running. Every session, shopping basket and login in the rest of this course is that observation with more machinery. Notice too that the deadline is the client's decision alone; the server is never told about it and cannot ask for more time.

  3. break

    Now put the two waiters under load. Start both, then drop three hundred requests into the mailbox at once, and report how many each answered.

    One answers all three hundred and the other dies partway through with FileNotFoundError, because it listed the directory, chose a file, and the other copy deleted that file before it could be read. Run it again and the roles swap. This is why the operating system, and not a convention, decides who owns an address: from chapter nine onward two programs cannot both claim the same port, and the second one is refused at the door rather than left to crash later.

in the wild

The roles nest. Your web server is a server to the browser and a client of Postgres and Redis in the same request, and none of those programs know which hat they are wearing. The one directional rule is why push notifications and WebSockets exist: both are ways of leaving a conversation open so the server can finally speak first. And the mailbox is not a toy analogy, it is roughly how a job queue works, which chapter sixteen builds on purpose.

Where this runs out

We now know who speaks first, who was there already, and who goes away afterwards. We know nothing whatsoever about what they say.

where this runs out

In the listing above the client sent the word time and got back a string, which worked because both halves were written by the same person in the same hour. The web is not like that. The two programs were written by strangers, years apart, in different languages, and they have never communicated about anything. A browser written this year has to be able to ask a server written fifteen years ago for a page, and understand the answer.

That requires an agreement fixed in advance and written down: what the client sends, byte for byte, what the server may send back, and how each side knows where the message ends. That agreement has a name, and reading it in full, in chapter six, turns out to be less work than most people expect.
