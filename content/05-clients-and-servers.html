Part three · the conversation

05 · Clients and servers

You have heard client and server, or front end and back end, often enough that they sound settled. What makes one program the client and the other the server is a single fact, so obvious that it is almost never said out loud: one of them was already running, and the other one started the conversation. The role belongs to the conversation, not to the machine. Your laptop is a client while you read a page and a server while your phone prints through it, and the only thing that decides which is which is who asked and who answered. The arrangement has a name, the client server model, and almost every design decision in the rest of this course follows from it.

One of them was already there

Chapter four got us as far as a machine and a path. There is a computer with a file on its disk, we can turn a name into its address, and chapter two gives us an ordered stream of bytes between two programs once they are joined up. What has not been settled is anything about the two programs themselves. One of them has the file and one of them wants it, and every other detail is open: which one starts, whether the machine holding the file is doing anything while nobody is asking, whether it knows you exist before you turn up.

Start with the machine that has the file. It cannot spring into life when you ask for something, because nothing on it would hear you. For your request to be heard, a program on that machine has to have been started already, and it has to have been sitting there, doing nothing, waiting for somebody to arrive. That gives the two roles. The program that starts the conversation, because it wants something, is the client. The program that was already running, and answers, is the server. This arrangement, one side waiting and the other side asking, is what the field calls the client server model. When you see the words client side and server side, or front end and back end, this is the line being drawn: the program that asked, and the program that answered.

That is the whole model, and five things follow from it. A server's ordinary condition is doing nothing. It spends nearly all of its life waiting, and waiting costs almost nothing, which you measured in chapter one when the sleeping process showed no processor use at all and still counted on time. A server does not know its clients in advance. It has no list of who might call; it finds out that you exist at the moment you arrive, and it usually forgets you again when you leave. The conversation can only be opened from one end. A server cannot ring you up, and this one shapes an enormous amount of what the web looks like: for years, a page that wanted to show you a new message had to keep asking whether anything had happened yet, because there was no way for the server to speak first. Clients are brief and servers are long lived. A client exists to ask one thing and then stops; the server was running before it arrived and is still running after it has gone. And clients arrive whenever they like, and there are many of them. A server with one visitor and a server with a thousand are the same program in a different situation, and dealing with that difference is most of part five.

It is a role, not a kind of machine

This is the part worth stressing, because the word server also names a kind of computer, and that makes people picture the role as something only a machine in a data centre can play. It is not. The role belongs to the conversation. The same computer can be a client in one conversation and a server in another at the same instant. Your laptop is a client while you read a page, and a server if you are sharing your screen, running a development server, or letting a phone in the house print through it. None of those change what the machine is. They change what it is doing in a particular exchange, and the only thing that decides which role it is playing is who initiated the request and who returned the response.

It is also worth saying that this arrangement is a convention rather than a law, because it is so common that it starts to look like one. Nothing in chapter two is asymmetric. Any address may send a packet to any other address, and the routers in the middle do not know or care which end started it. Systems where every program does both jobs at once are real, and file sharing networks are the well known example; the arrangement is called peer to peer. Client and server won because it is easier to reason about, and because of the practical asymmetry from chapter four: most machines sit behind a shared public address and cannot be reached from outside at all. A design where everyone must be reachable was possible in 1980 and is awkward now.

Chapter twelve returns to the other meaning of the word, the physical computer built to run programs like this all day. Everything in this chapter is the program.

Watching the two roles run

We do not yet know how a program listens for someone arriving over a network, because that is chapters eight and nine. So here the two programs talk through a directory on the disk, which is something chapter one already covered. The channel is a placeholder. The roles are the real subject.

The waiting half checks a mailbox directory for requests, answers each one into a matching file, and goes back to checking.

The starting half writes one request, waits for its answer, and exits.

Start the waiting one in a terminal window and leave it alone, then in a second window ask it three things.

While that happened, the first window filled in.

The process ids are the part to read closely. Three separate client processes ran, 59672, 59673 and 59674, each of which existed for a fraction of a second and then died. Every one of them was answered by process 59632, which was there before any of them started and is still there now. That is the asymmetry, in numbers.

The third answer matters too. The client asked something the server had never been taught, and the server answered anyway, saying what was wrong. It did not crash and it did not go quiet. A server that stops working because somebody sent it something unexpected is a server that any stranger can turn off, and strangers are the entire audience. Now replace that directory with a network connection and you have a web server. That substitution is chapters eight through ten, and nothing in the shape above changes, which is the reason for showing it before the machinery arrives.

Check it yourself: ask when nobody is listening

Stop waiter.py with control C, then run the client on its own.

terminal two
$ python3 asker.py time
process 60336 asked 'time' and is now waiting
nobody answered. is waiter.py running?

Nothing the client can do will produce an answer. It cannot start the server, because starting a program on somebody else's machine is not something a network lets you do, and that is deliberate. The server has to already exist, which is the claim this chapter opened with, and it fails in exactly the way a browser fails when a site is down.

Then look at how many programs on your own machine are currently playing the server role. On macOS or Linux:

terminal
$ lsof -nP -iTCP -sTCP:LISTEN
COMMAND     NAME
rapportd    *:50108 (LISTEN)
ControlCe   *:7000 (LISTEN)
ControlCe   *:5000 (LISTEN)
...and more, from applications you installed and forgot about

The names have been trimmed here, because the full list names everything the author has installed. The word LISTEN is the operating system's record of a program that has asked to be told when somebody arrives, which is the mechanism chapter nine is about. The point of looking is the count. You did not start most of these and you would not describe any of them as a server, and yet each one is the waiting half of some conversation. Your laptop is a client and a server at the same time, right now, and which one it is in any given exchange depends only on who asked.

What the roles do not tell you

We now know who speaks first, who was there already, and who goes away afterwards. We know nothing whatsoever about what they say.

where this runs out

In the listing above the client sent the word time and got back a string, which worked because both halves were written by the same person in the same hour. The web is not like that. The two programs were written by strangers, years apart, in different languages, and they have never communicated about anything. A browser written this year has to be able to ask a server written fifteen years ago for a page, and understand the answer.

That requires an agreement fixed in advance and written down: what the client sends, byte for byte, what the server may send back, and how each side knows where the message ends. That agreement has a name, and reading it in full, in chapter six, turns out to be less work than most people expect.
