Part one · one computer

01 · Computers, programs, and programming

Programming is usually defined as writing instructions that tell a computer what to do. The definition is correct, and it hides everything: what a computer is, what an instruction is, and what happens when one is told. This chapter takes it apart on a single computer, which for a long time was the only place a program could be.

Instructions that tell a computer what to do

Here is the smallest case of it there is: one instruction, in a file, and a command that carries it out.

Something found a file on a disk. Something copied its contents somewhere else. Something created a record that did not exist a second earlier, decided when your work would happen, paused it partway through, started it again, and threw the record away when it was done. Then the word appeared. We call all of that "run", and the word explains nothing. Three things have to be pulled apart before it does: the machine, the file, and the program in the middle that turns one into the other.

A computer follows one instruction at a time

Underneath every piece of software you have used there is a part that does arithmetic and very little else. It is called the processor, and in most writing the CPU. It can add two numbers, compare two numbers, copy a number from one place to another, and decide which instruction to look at next. That list is close to complete. Everything else is built out of those few moves, repeated.

The numbers live in memory, a very long row of numbered boxes each holding a small value. The number of a box is its address, and an address is how everything inside a computer refers to everything else. When your program says "the total", what is really there is a box number.

The processor also keeps one piece of private bookkeeping, and it is the important one: the address of the next instruction to carry out. That single number is what turns a pile of instructions into a sequence. Fetch the instruction at that address, do what it says, move the number on by one, repeat. When a program needs to go back and do something again, one instruction writes a different value into that number and the machine carries on from the new place, with no idea that anything unusual happened. There is no cleverness in the loop and no plan in it. A laptop runs it a few billion times a second, and that speed is the only reason the result looks like thought rather than like counting.

A machine small enough to watch

None of that is visible on a real computer, because it happens too fast and too far underneath. So here is a machine with the same parts and none of the speed: eight boxes of memory, one number saying where it has got to, and five kinds of instruction. It is written in Python because the point is the shape of the loop, not the syntax.

Look at the counter column and nothing else. It reads 0, 1, 2, 3, 4, then 2 again. That jump backwards is the entire mechanism of a loop. There is no looping instruction anywhere in the machine and no notion of repetition. One instruction wrote a smaller number into the counter, and the same fetch and carry out loop walked over the same three instructions a second time. Every loop you have written comes down to that, and so does every if, every function call, and every method on every object.

The same loop, in the language you are using

That is a toy, and the obvious objection is that Python is nothing like it. Python has no boxes and no counter. It has for, which is a real looping instruction, so the machine above must be an analogy rather than the truth.

It is not an analogy, and Python will tell you so itself. Here are four lines with a loop in them.

The word python3 in python3 loop.py is not the computer and it is not your program. It is another program, sitting on your disk, whose job is to read your file, translate it into instructions of its own, and then run exactly the fetch, do, advance loop above over them. Those instructions are not a secret. dis, which is short for disassemble, prints them.

The left column is the line of your file; the next is the address of the instruction, which is the toy machine's counter under its real name. Read address 42. JUMP_BACKWARD 8 (to 28). Your for loop was translated into a write to the counter that sends it back to instruction 28, which is what jump_if did in the toy.

So programming, the third word in the title, is writing in a form convenient for a person which some other program turns into a form convenient for the machine. Python translates each time you run the file. Other languages translate once, in advance, and hand you the machine instructions directly. Either way, what runs at the bottom is the loop you just watched twelve steps of.

A program is a file until something runs it

Before you run it, your program is a file: a named stretch of bytes on a disk, with nothing about them that makes them a program. Nothing happens inside hello.py while you are not looking at it. Something has to pick it up and make it into activity, and that something is a program too. The operating system is the program whose job is running other programs, and it was already running before you typed anything.

When you press enter it does several separate jobs. It finds the file, reserves memory and copies the instructions in, reserves more memory for the values the program will make up as it goes, and writes down which files it has open, what it may touch, and the address to start at. Then it lets the processor loose. That bundle of memory and bookkeeping is a process: a running program plus everything the operating system has to remember about it. Start the same file twice and you get two processes that share nothing and cannot see each other.

You can read that bookkeeping. This program counts once a second, which gives you time to look at it from outside. The number os.getpid reports is the process id, how everything outside the process refers to it.

Leave it running and open a second window. ps prints the operating system's own record of it.

STAT starts with S, for sleeping: the program is using no processor at all. It asked to be woken in a second and the operating system took it off the schedule until then, which %CPU confirms. RSS is the memory it holds right now, about nine megabytes for a program that adds one to a number, and the reason is the next line down. lsof lists the files the operating system wrote down as open for this process, and the entry marked txt is the six megabyte Python binary. Almost none of that memory is your code. It is the program reading your code.

One more job, and it is the one nobody mentions. Your machine has a handful of processors and a few hundred programs that all want to run. So the operating system lets one process use a processor for a few thousandths of a second, interrupts it, writes down exactly where it had got to, and hands the processor to a different process. Later it puts the first one back exactly as it was, and that process carries on with no way of telling it was stopped. Deciding who runs next is scheduling. Saving one process and restoring another is a context switch, and it happens thousands of times a second.

the puzzle

Right now your laptop is running well over a hundred programs: a browser, a music player, a clock, a dozen you did not start yourself. It has maybe eight processors, and often fewer that are any good. Eight cannot run a hundred at once.

So how does a machine with eight processors run a hundred programs and look like it is doing all of them at the same time?

Check it yourself: more programs than processors

Turn taking is a claim you cannot check by reading, so measure it. This runs the same fixed piece of arithmetic in one process, then two at once, then four, timing each round from start to finish.

Run it. On the machine this was written on:

a run of turns.py
this machine reports 18 processors
 1 copies took  0.75 seconds
 2 copies took  0.75 seconds
 4 copies took  0.75 seconds
 8 copies took  0.74 seconds
16 copies took  1.37 seconds
32 copies took  3.30 seconds

The digits are not the point; the shape is, and it has two ends. At the start, adding copies is free, because idle processors were sitting there and the operating system had somewhere to put the extra work. Then it climbs in proportion, because there is no longer a free processor for each copy, so each one spends part of the round stopped, holding its place.

Both ends would be impossible if this chapter were wrong. If each program owned a processor from start to finish, two copies would take twice as long as one and the flat part could not exist. If processors were unlimited, thirty two copies would cost the same as one and the climb could not exist. What you measured is turn taking, from outside.

if the knee comes early

Many laptops have two kinds of processor, some fast and some built to use less power, and the reported count adds both. So the flat part can end well before the number suggests. The shape still holds.

Exercises

  1. predict

    Copy turns.py and change one line, WORK, to "import time; time.sleep(0.75)". Each process now takes the same three quarters of a second and does no arithmetic at all. Write down all six timings before you run it.

    Every row comes out at about 0.8 seconds, including thirty two copies. Sleeping is not work the scheduler has to find a processor for, so the count of processors stops mattering. If you predicted a climb, the thing you were really measuring in the check was contention for a processor, not the cost of a process.

  2. build

    The toy machine cannot multiply. Write it a program that computes three times four using only set, add, jump_if, show and stop, predicting the step count before you run it. Widen the memory[:2] in the printing to see the boxes you use.

    Twelve, in fifteen steps. Multiplication is repeated addition driven by a counter, which is why the earliest processors shipped without a multiply instruction and nobody was stuck.

  3. break

    Start slow_count.py and leave it counting. In another window edit the file, changing count += 1 to count += 100, and save. Watch the first window.

    It keeps counting by one. The process is a copy of the instructions, made in memory when it started, with no connection to the file any more. This is why a running server ignores your edits, and why every deploy later in this course has to stop something and start it again.

in the wild

Activity Monitor and Task Manager are ps with a refresh and a sorted list, and htop is the same in a terminal. A Docker container, which arrives later in this course, is one or more ordinary processes exactly like the one you inspected, given a restricted view of the disk and the network by the same operating system that schedules them.

Where this runs out

where this runs out

Everything above is inside one box: a processor fetching, a file that is inert until the operating system builds a process around it, and turns handed out fast enough to hide how few processors there are. Almost no software anyone uses is like that, because the programs we care about are the ones other people can reach, and other people are not sitting at your laptop. A process here cannot pass a memory address to another machine, because box number 4,096 on your computer has nothing to do with box number 4,096 on anyone else's, and it cannot write to the other machine's disk because it cannot see it.

Two machines, no shared memory, no shared disk, and a need to move bytes between them anyway. That is the next chapter.
