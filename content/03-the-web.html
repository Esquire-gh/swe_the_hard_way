Part two · the machines get connected

03 · The web

Most people use the internet and the web to mean the same thing, and for everyday purposes nobody minds. Here the difference is the whole chapter. The internet moves bytes and has no idea what they mean. The web is one agreement about what some of those bytes mean, one of many that were tried, and it arrived late with no advantage anybody could see at the time. This chapter is about what it had that the others did not, and it is one decision.

The internet is not the web

The last chapter ended with bytes arriving reliably and in order, and with the receiving program having no idea what they were. That is the internet: the machines, the addresses, and the promise that bytes you send will arrive. It was running for twenty years before the web existed and would carry on running if the web disappeared tomorrow.

What makes a bare network useful is an agreement, made in advance, about what the bytes will mean. An agreement between two programs about what to send, in what order, and what it signifies is called a protocol. TCP is one, and its subject is delivery. The interesting ones sit on top of it, and their subject is whatever people wanted to do.

Many were built and several are still running. Electronic mail arrived in 1971 and delivers a document to one person's box. File transfer arrived the same year and lets you take a copy of a file if you already know the machine, the directory and the name. Usenet carried discussion, and Gopher, which arrived the same year as the web, offered menus of documents you could walk down into. They differ in every visible way and they share one thing. In all of them a document is a dead end: once you are reading it, the document cannot point anywhere. Whatever structure exists lives outside the documents, in a menu or a directory listing that somebody has to maintain.

Four refusals

Text that points at other text was not a new idea. Working systems had existed for decades, and by the late 1980s people used them daily. They had one property in common, and it was considered the mark of a serious system: their links were guaranteed. The system knew every link, refused to let you point at something that was not there, updated links when a document moved, and removed them when it was deleted.

That guarantee puts a hard ceiling on how far a system can spread, because keeping every link honest means something has to know about every document and every link at once. Workable on one machine. Not workable across machines owned by people who have never met. The proposal Tim Berners-Lee wrote at CERN in March 1989 gave it up, and three other things with it. Each of the four is a refusal to do what the established systems did.

Links are allowed to break. A link is a one way pointer that names a document, and nothing checks that the document exists until somebody follows it. No registry, no cooperation, no repair when the target moves. Following a dead link fails, and failing is an ordinary outcome rather than a fault in the system. This is where 404 not found comes from, and it is the decision that let the thing span machines nobody coordinated.

Anyone may publish without asking. There is no central list to be added to and no authority to apply to. You put a file on a machine, run a program that hands it out, and it is on the web.

Anyone may link without asking. Pointing at somebody's document needs no permission and no cooperation from them, because a link is only a name written inside your own document. They never find out unless you tell them.

The format describes the document, not the screen. A page says that a run of text is a heading, and each machine decides for itself what a heading looks like. Given a laboratory full of incompatible computers, that was not a nicety, it was the only way one document could be readable on all of them.

Then CERN put the whole design into the public domain in 1993, free for anyone to implement or sell, the same year the University of Minnesota announced licence fees for running a Gopher server. Gopher had been ahead. Within about two years it was finished. The web did not win on elegance. It won because it asked nobody for permission, and it could do that only because it had given up the guarantee everyone else thought was essential.

What a link actually is

Strip the decoration away and a link is a name written inside a document. Three notations for the same thing, one of which you are about to build:

That is the whole mechanism. The page contained a name. Something read the name out of the page and asked for it, and a machine at the other end answered with a number saying how it went. Nothing in the first page knew whether the second one existed, and the third command shows what the answer is when it does not. Notice also that the address in the page and the address that answered are not the same string, which is a hint the next chapter picks up.

A library that lets its links break

Hypertext with everything else stripped away is small enough to build. Here is a library of documents where any line beginning with an arrow names another document, and nothing anywhere checks that the named document exists. The documents live in code/03-the-web/library/, and this is the first one.

The program starts at welcome, reads whatever it is pointed at, and keeps going until there is nothing left to follow. Give it a network instead of a folder and this is a crawler, which is how every search engine finds out what exists.

Three things in that run, and all three are the web. The structure is inside the documents: there is no index and no menu, and the only way to know that welcome leads to networks is to read welcome. Adding a document means writing a file and having something point at it, and nobody has to be told.

Links go one way. networks points at packets and packets points back, but those are two separate one way links that happen to face each other. Nothing about the first creates the second, and packets has no way of knowing who points at it. That asymmetry is the second exercise, and it is worth more than it looks: knowing who links to a page is not a lookup, it is a scan of everything, which is a large part of what a search engine is for.

A broken link is a result, not a crash. the-one-that-moved is missing, the walk carries on, and the program finishes and reports it. To make the guarantee the older systems made, every one of these files would have to be registered somewhere, and creating a file would stop being a private act.

Check it yourself: take a document away

Move one of the documents out of the library and run the walk again.

terminal
$ mv library/packets.txt library/packets.txt.away
$ python3 follow.py
[welcome] A library of four documents, three of which exist.
          points at networks
          points at packets
          points at the-one-that-moved
[networks] A network moves bytes between machines and has no opinion about them.
          points at packets
[packets] there is no document with this name
[the-one-that-moved] there is no document with this name

documents read: 2
links that point at nothing: ['packets', 'the-one-that-moved']

Nothing else in the library noticed. welcome still reads correctly and still lists three links, one of which now fails. No file had to be edited, no index had to be rebuilt, and the walk still ran to the end. That is the trade written out in full: in exchange for accepting that some fraction of links will be dead at any moment, publishing and linking become things you can do alone. The web is the largest thing people have built out of that one exchange.

Put the file back with mv library/packets.txt.away library/packets.txt when you have looked.

Exercises

  1. predict

    You want to answer the question which documents link to packets. Before writing anything, say how many of the library's files have to be read to be sure of the answer, and say what the equivalent number would be for a page on the real web.

    All of them, every time, because a document records what it points at and nothing records what points at it. On the web the equivalent is every page that exists, which is why the answer to that question is a company with data centres rather than a query.

  2. build

    Write who_links_to(name), which returns every document in the library that points at name. Run it for packets, networks, welcome and the-one-that-moved, and print how many documents it had to read each time.

    Three reads for every question, including the one about a document that does not exist. Two results are worth stopping on. the-one-that-moved has a link pointing at it and no file behind it, which is a dead link seen from the other end. And welcome, the document everything starts from, is linked from nothing at all; on the real web a page like that is invisible, because a crawler that has never been given its name has no way to reach it.

  3. break

    Take the memory out of the walk: delete the seen set and the two lines that use it. Predict what happens to networks and packets, which point at each other, then run it with a limit on the number of reads so you can watch rather than reach for control C.

    The queue never empties. The two documents feed each other names forever, and after twelve reads there are still names waiting. Nothing is broken and no rule was violated: the library is a graph with a cycle in it, and one way links mean nobody can see the cycle from inside a document. Every crawler on the internet carries this set, and how large it can get is one of the real problems in running one.

in the wild

The first refusal created industries. Link checkers exist because links rot, and the Internet Archive's Wayback Machine exists to keep copies of pages before they do. Google started as who_links_to run over everything, with each link counted as a vote. And the crawler you just wrote is the same shape as the one that fetched this page for a search engine, plus rate limits, politeness rules and a very large seen set.

Where this runs out

There is a gap in the library, and it is doing quiet work. When a document says -> packets, the program turns that name into a filename in a folder on this machine. That is fine here, because there is one machine and one folder. On the web there is no such folder.

where this runs out

The document being pointed at might be on a machine in another country, owned by a stranger, and the pointer has to work anyway. So a name on the web has to carry more than a filename. It has to be enough to find one particular machine out of every machine on earth, then ask that machine for one particular document, and it has to do that from a page written years ago by somebody who has never heard of you.

The curl run above already showed the seam: the name in the page was iana.org/domains/example and what answered was www.iana.org/help/example-domains. Two different strings, one document.

Which raises the question this chapter has been avoiding. When you point at a page, where is that page actually sitting, and how does anything find the machine it is sitting on? That is chapter four.
