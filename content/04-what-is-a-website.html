Part two · the machines get connected

04 · What is a website?

The word website sounds like a place. It is not a place. Somewhere there is a computer, probably in a rented rack in a building with good air conditioning, running an operating system and processes exactly like the ones on your laptop, and on its disk there is a file. When you visit a page, a program on that machine reads that file and sends the bytes back to you. That is the whole of it. The two hard parts of that sentence, finding the machine and naming the file, are this chapter.

A website is a folder on a computer somebody else runs

Start with the one you are looking at. This site is a folder of files in a repository, and the page in front of you is one of them.

Those files are on the author's laptop. They are also on a computer belonging to GitHub, which is what makes them a website rather than a folder, and you can ask that computer about itself. curl -I asks for a page and prints only the notes that come back with it rather than the page.

A machine answered, said which program answered, said what kind of thing it is sending, and said when the file was last written. That last line is the moment the author ran the build, so the file on GitHub's disk and the file on the laptop really are the same file, copied. There is no website object anywhere. There is a directory, a program that hands out what is in it, and a machine that is switched on.

So the rest of the chapter is the two hard parts. A link written years ago by a stranger has to find one machine among all the machines on earth, and then get one file off it.

A web address is two questions in one

The scheme says which set of rules to use for the conversation, and https means the rules in chapter six with the conversation encrypted. The host says which machine to have the conversation with, and it is the part that has to be turned into something the network can route to. The path says what to ask that machine for once you are connected.

The path looks like a filename in a folder because in 1991 that is exactly what it was: the program on the far machine took the path, stuck it on the end of a directory name, and read that file off the disk. The site you are reading still works that way. Much of the web stopped long ago, and chapter eleven is about when and why, but the shape of the name never changed. The whole thing together is a URL, a uniform resource locator, which is a formal way of saying an address that works from anywhere.

The second question is somebody else's problem until the first is solved. Which machine?

Every machine on the network needs a number

Routers forward packets by reading the destination written on them, so every machine reachable on the internet needs a number no other machine is using. That number is its IP address. The old and still common form, IPv4, is four numbers between 0 and 255 with dots between them, like 208.80.154.224. Thirty two bits, about 4.3 billion machines, and in the 1980s nobody expected to need one per telephone. They ran out. The replacement, IPv6, is a hundred and twenty eight bits written as groups of hexadecimal digits separated by colons, like 2620:0:861:ed1a::1, and most machines now have both.

No router could hold a list of billions of machines, and none has to, because addresses are handed out in contiguous blocks. A router's table says something closer to "anything starting 208.80.152 goes out of link three", so it holds around a million ranges instead of billions of addresses. That is how a machine three hops away can forward a packet toward a destination it has never heard of.

Your own machine is probably not in that scheme at all. Ranges starting 192.168 and 10. are set aside as private: they are not unique, and no router on the internet will forward to them. The box your internet arrives through has one real public address that everything in the building shares, rewriting the sender's address on the way out and undoing it when the reply comes back. This is network address translation, and it is why 4.3 billion addresses have lasted this long.

carry this forward

That arrangement works in one direction. Your machine can start a conversation with anything on the internet, and nothing on the internet can start one with your machine, because no address reaches it. When you write a working web server in chapter ten and none of your friends can visit it, this is why. Writing a server and putting it somewhere the world can reach are two separate jobs, and only the first is about programming.

Nobody can remember numbers, and numbers move

Numbers are correct and unusable. People cannot remember them, and worse, they change: a site moves to a different machine, or to twelve machines in different countries, and every link ever written to it has to keep working. So something has to turn a name into a number, and the first version was exactly what you would guess. One file listed every name on the network and its address, maintained at one research institute, and every machine downloaded a fresh copy from time to time.

It failed for the reason the last chapter made familiar. One central thing everybody has to coordinate with does not survive growth: the file got large, it was out of date the moment it was copied, and adding a machine meant writing to someone and waiting. The replacement, designed in 1983, splits the names up and hands out authority over the pieces. It is called the Domain Name System, DNS, and you read a name backwards to see the shape.

In en.wikipedia.org, the last part is org. A small set of machines called the root servers know nothing about wikipedia, but they know which machines are responsible for org. Those machines know nothing about the en part, but they know which machines are responsible for wikipedia.org. Those machines, run by the people who run wikipedia, know the address. Nobody holds the whole list, and adding a name inside wikipedia.org means telling nobody outside wikipedia.

Your own machine does not walk that chain. It asks one machine, called a resolver, which walks it and then remembers the answer for a stated number of seconds. That period is the time to live, and it is why the first lookup of a name is slow and the next thousand are instant. All of this is programs on machines sending each other messages over the network from chapter two. There is no separate magic layer.

The file DNS replaced is still on your machine

That single global list did not disappear. Every machine still carries a private copy, it is consulted before any question goes near the network, and whatever it says wins.

This is why localhost resolves instantly and works with no network at all. It is also a tool: add a line here and that name means whatever you say on this machine and nowhere else, which is how people point a real site's name at a copy running on their own laptop. On Windows the same file lives under System32\drivers\etc.

Looking a name up

Python can ask the operating system for a lookup, and the operating system checks that file, then asks the resolver.

Your addresses for the first two will differ from these, and may differ from each other on consecutive runs, and that is the first lesson in the output. One name is not one machine. example.com came back with four addresses, two of the old kind and two of the new, from a single question. A busy site answers with several, and often with different ones depending on where the question came from, so you are sent to a machine near you. The name names a service, and the service can be as many machines as it likes.

localhost points at the machine it is typed on. Packets sent to 127.0.0.1 never reach a network card at all, because the operating system loops them straight back into itself, which is why everything from chapter eight onward can be tested with both sides of a conversation on one laptop.

The last line fails, and it fails the way a broken link did in the last chapter. A name that resolves to nothing is an ordinary answer, handled and reported, rather than a fault in the system.

Check it yourself: watch the chain, then watch the memory

Two claims to test. First, that no single machine knows the whole list. dig +trace walks the chain one step at a time and shows every answer.

terminal
$ dig +trace +nodnssec wikipedia.org A
.                   56789   IN  NS  a.root-servers.net.
.                   56789   IN  NS  b.root-servers.net.
                    ... eleven more ...
org.                172800  IN  NS  a0.org.afilias-nst.info.
org.                172800  IN  NS  b2.org.afilias-nst.org.
                    ... four more ...
wikipedia.org.      3600    IN  NS  ns0.wikimedia.org.
wikipedia.org.      3600    IN  NS  ns1.wikimedia.org.
wikipedia.org.      180     IN  A   208.80.154.224

Read it as three questions and an answer. The root servers all declined to answer: what they returned is a list of who to ask about org. The org servers declined too, and named who is responsible for wikipedia.org. Only wikimedia's own machines produced an address.

The numbers in the second column are the times to live, in seconds. Who runs org is good for 172,800 seconds, which is two days, because it almost never changes. The address is good for 180 seconds, because they may want to move it at short notice.

Second claim: your resolver remembers. Ask for a name nobody nearby has asked for recently, then ask again.

terminal
$ dig nlnetlabs.nl +noall +answer +stats | grep -E "IN|Query time"
nlnetlabs.nl.       240     IN  A   128.140.76.106
;; Query time: 137 msec
$ dig nlnetlabs.nl +noall +answer +stats | grep -E "IN|Query time"
nlnetlabs.nl.       234     IN  A   128.140.76.106
;; Query time: 3 msec

A hundred and thirty seven milliseconds became three, which is the difference between walking the chain and answering from memory. The proof is the number in front of the address: it was 240 and is now 234. That is not a fresh answer, it is the same answer with six seconds knocked off its life, counting down toward the moment the resolver has to go and ask again.

One more, because it is worth knowing you have a choice. dig @1.1.1.1 example.com +short asks Cloudflare's public resolver instead of the one your provider handed you, and @8.8.8.8 asks Google's. Which resolver you use decides who sees every name you look up.

if dig is not on your machine

host wikipedia.org or nslookup wikipedia.org will give you the answer without the journey.

Exercises

  1. predict

    You ask your resolver for a name it has never been asked for, three labels long, like docs.example.org. Before running anything, write down in order which machines get asked, and how many separate questions the resolver has to send before it can answer you.

    Three, one per label from the right: the root servers for org, the org servers for example.org, and example's own servers for the full name. Each question is a round trip over the network, which is what the 137 milliseconds above was made of, and it is why the answer is worth remembering afterwards.

  2. build

    Build the system out of three dictionaries: a root that knows only who handles org, an org server that knows only who handles wikipedia.org, and wikipedia's server that knows the addresses. Write resolve(name) to walk from the root one label at a time from the right, returning the address and how many servers it asked. Then add a cache with a time to live, and count the servers asked over a thousand lookups of one name with and without it.

    Three servers asked per lookup, and a name nobody handles costs two, because the org server can say no on its own authority. Over a thousand lookups the count goes from 3,000 to 3. Notice that no server in your three dictionaries knows more than one thing, and that the whole design works precisely because none of them has to.

  3. break

    Now move the site. Change the address held by the authoritative server sixty seconds into a run and keep looking the name up once a second for five minutes. Count how long the wrong address is served, then set the time to live to one second and run it again.

    With a three hundred second life the move takes effect two hundred and thirty nine seconds late, and every lookup in between returns an address that is no longer right. With a one second life the wrong answer lasts one second and costs 900 questions instead of 3. No setting is correct, only a trade between how fast you can move and how much work everybody does, which is why the 180 in wikipedia's answer above is a decision somebody made on purpose.

in the wild

The many addresses in the example.com lookup are a content delivery network: the name resolves to whichever copy is nearest to whoever asked. Web hosting is the "somebody else" in the title of the first section, and GitHub Pages, which serves this site, is the plainest form of it, a folder in a repository handed out by a machine that is already switched on. And the short time to live in the last exercise is what every deployment guide means when it tells you to lower it the day before you move.

Where this runs out

We can now find the machine, and we have a path naming what we want from it. A name became an address, an address is something routers can move packets toward, and chapter two gave us an ordered stream of bytes between two programs once they are connected.

where this runs out

What we still have no account of is the conversation itself. Two programs, one of which has the file and one of which wants it. Something has to happen between them and every part of it is undecided. Which one speaks first. Whether one was already running before the other appeared, or whether they started together. Whether the machine with the file is doing anything at all when nobody is asking.

Those questions have names, and the names come with a model so established it is rarely explained. Before looking at what the two programs say to each other, chapter five is exact about who they are.
